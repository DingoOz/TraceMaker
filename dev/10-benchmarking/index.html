    scripts/fetch_fixtures.sh pins the three default sets to the commits the 0.8.0 results were measured on (Freerouting d216f90 of 2026-09-30, DAC 2020 bee2888, KiCad 10.0 7a7d026), so a fresh clone gets the same boards, tiers and Freerouting result file; TM_FIXTURES=latest or TM_REF_<SET>=<commit> overrides a pin.     Building unrouted fixtures¶

    strip_routing in bench/prepare_dac2020.py removes every top-level segment/arc/via node and keeps everything else byte for byte, including zones. Both DAC2020 and bench/prepare_demos.py then prepare the unrouted derivative through bench/prepare_inputs.py: private native pcbnew.LoadBoard/SaveBoard conversion without refill, deterministic identity repair and item ordering, then native refill/DRC. Unique nonzero native source UUIDs are preserved; loader-generated, missing, zero and duplicate identities are repaired before the first authoritative refill. Stale fill caches are discarded, not zone geometry. This does not change the all-tracks/arcs/vias strip policy or add thermal-array retention.

    Fixtures contain <out>/<name>/unrouted.kicad_pcb, byte-exact copies of the source .kicad_pro/.kicad_dru when present, and preparation.drc.json. DAC2020 also keeps its byte-exact human raw.kicad_pcb and Specctra fixture. Preparation never rewrites source/human boards. Work is private and the runnable board is published last; failure removes only generated unrouted board/rule/report artifacts, so an earlier successful board cannot masquerade as the requested input. Missing current rules do not reuse a previous fixture's rules. DRC findings are retained as evidence, not treated as a requirement that the unrouted input be clean.

    Tools and reproducibility (D107). Host Python 3.8+ and its standard library suffice; conversion additionally needs KiCad 10's pcbnew Python bindings, with the exact major.minor.patch version of the selected CLI. KICAD_CLI and KICAD_PYTHON select executable paths (not shell command strings). Without overrides, preparation finds kicad-cli on PATH, falling back to scripts/kicad-cli; the repository ships an executable scripts/kicad-python companion using the same TRACEMAKER_KICAD_IMAGE (default kicad/kicad:10.0.6), home/current-directory mounts and caller UID/GID as the CLI wrapper. Native CLI installs use the host Python, or KiCad.app's bundled Python on macOS; set KICAD_PYTHON when pcbnew belongs to a different interpreter. A version mismatch fails before loading/refilling the board. For Docker, source, checkout and output must be under $HOME or the mounted current directory (the wrappers' mount contract); no personal paths or additional packages are required.

    With the same source/rule bytes, fixture name and native tool versions, repeated preparations should yield byte-identical boards and rules. Native DRC report ordering/counts are not promised byte-identical (§4, judge noise); report hashes are not a determinism claim. Native conversion/refill intentionally changes the prepared input compared with the old strip-only scripts: rebuild inputs and measure fresh paired baselines against the same new fixtures, never compare old cached inputs with newly prepared ones.

    Fixture-independent controls (own generated legacy board, no downloaded/redistributed PCB) are:

    python3 tests/integration/fixture_preparation.py
python3 tests/integration/fixture_preparation_native.py

    The native control first converts legacy zero-timestamp zones without refill and reports the missing/zero zone IDs, then invokes the actual demo entrypoint twice and compares board/project/custom-rule bytes, nonzero unique identities, preserved zone geometry, native fill presence and untouched source bytes. KiCad unavailability skips the native test; conversion/preparation failures do not. The place-and-route sets (unlocked footprints reset to a pile) remain built by bench/make_place_sets.py.

    2. Metrics per board¶

    Metric Definition
    Clean pass 100% connections routed and zero added KiCad DRC errors (input vs output, kicad-cli pcb drc)
    Completion routed connections / routable connections (excluding pins proved dead)
    Added DRC errors physical violation multiset difference, grouped by KiCad type for display (D106)
    Vias, wirelength, bends totals; also normalised to the reference routing where it exists
    Wall time, work units engine-reported, with hardware recorded: the time is the whole route job (every portfolio variant, D86), the work units (expansions) are the winning variant's only
    Work profile per phase (setup, first pass, negotiation, clean-up): expansions, flood cells, searches, cell checks, fixed-copper checks, cost-field cells and fields, commits, rips; deterministic, in the route JSON as work (winner) and work_all_variants (D88)
    Route CPU time user + system seconds of the tracemaker route process (cpu_s per board, cpu_seconds per run)
    Placement (P&R set) HPWL, lower-bound gap, crossings, courtyard overlaps (must be 0), moved parts
    Style (informational) per board style: connections, bends per connection, acute angles, stair-steps, short and off-angle segments, detour ratio, long detours (definitions in doc 05 §39.2), measured on the new copper by the engine and on the fixture's own routing (style_ref) by tracemaker style; totals in summary.json (style, style_ref, style_same_boards) and report.md; compare_runs.py lists boards whose metric changed. Never a gate
    Determinism output hash per board at 1 and N threads, GPU on/off

    4. Harness (bench/)¶

    bench/run.py routes each board of a set with a snapshot of the engine binary, judges input and output with kicad-cli pcb drc, and writes bench/results/<run-id>/{boards.jsonl, summary.json, report.md, boards/} (summary.json feeds the progress site). bench/compare_runs.py compares two runs board by board and checks the gates of §5.

    Option Effect
    --set NAME the boards of bench/sets/NAME.txt (names the set in the summary)
    --work N deterministic work budget per board, no knowledge base; --time becomes a safety stop (3,600 s). Every portfolio variant gets the whole budget, so a board does up to eight times N
    --threads N router threads per board; with --work the default is the cores per job (at most 8), since the output does not depend on it (D47), but 1 with --halving in the route options, whose budget shares follow the thread count; without --work it is also the portfolio size (default 1)
    --refill KiCad refills zones before judging input and output; needed whenever fills may be stale (--soft-zones)
    --route-args=... extra tracemaker route options (also TM_ROUTE_ARGS)
    --fixtures DIR boards from DIR/<name>/unrouted.kicad_pcb instead of PCBench; a .kicad_pro/.kicad_dru beside it is copied next to the output so KiCad judges with the board's rules
    --tier, --limit, --seed sample PCBench boards by Freerouting tier instead of a set

    Sets (bench/sets/):

    Set Boards Command When
    quick the 30 PCBench tier-A boards of --limit 30 --seed 1 --set quick --work 1000000 --route-args "--variants 1" (≈ 30 s with --jobs 4) every routing change
    mid 11 large, hard PCBench boards --set mid --work 20000000 changes to search, plans or rip-up, which can move results at 20 M while quick stays identical
    planes 7 KiCad demos with zone fills plus tests/boards/plane_smd, routing stripped bench/prepare_demos.py --set planes, then --fixtures build/demos --set planes --work 3000000 --refill, once plain and once with --route-args=--soft-zones changes to zones, planes and plane targets

    Comparing. bench/compare_runs.py BEFORE AFTER [--expect-identical] lists every board whose routed output differs or got worse, the clean-pass and completion totals and router seconds, and exits 1 if a gate fails. --expect-identical adds "every routed board byte-identical" for speed-ups and refactors. Build the "before" binary from the base commit (a clean origin/main worktree) and run both on the same machine. Route CPU time is printed per board and in total. When both runs used the same --work, boards whose output is byte-identical did the same work, so their CPU change is run-to-run noise or a change in speed that leaves the output alone; the report prints that band and lists the boards (and the total) that moved beyond it, and at least 10 %. When every identical board moved the same way by more than 10 % it says that too: one pair of runs cannot tell a faster binary from a quieter machine, a second run of one binary can. All of it is a pointer for gate 5, not a failure.

    Not built (planned in the first version of this document): manifest files, a standard (~300 boards) and full tier as named sets, bench/report.py with an HTML dashboard, and paired statistics (sign test, bootstrap interval). Seeds: best-of-1 is the headline; best-of-5 is reported separately where a comparison needs it (PCBWorld reports baselines as best of 5).

    Judge noise. KiCad's solder_mask_bridge count can differ between runs on byte-identical boards when zones are refilled (StickHub: 17, 15 and 13); read a change in that type alone as noise.

    Native error gates (D106). bench/drc_judge.py compares physical error instances, not totals by type: removing one clearance cannot cancel a new clearance somewhere else. Item ordering and regenerated UUIDs or footprint references do not change an identity when positions are available; kind, net, layer, geometry description and position do. Coordinates and dimensions are normalised to nanometres from report units; items without positions use UUIDs as a fallback. Duplicate findings retain their multiplicity. Violation-level layer context is also identity: multilayer zone/PTH pad labels may not identify the affected layer of a thermal defect. Changing its layer is a new instance; changing its minimum/actual spoke-count diagnostic on the same layer is not.

    Routing gates include error-severity starved_thermal and isolated_copper even if KiCad names only pads or zones: routed copper can damage a refill without appearing in its report. Other pad/graphic-only changes remain diagnostic, including pad-only solder-mask refill noise and net-propagation clearance changes. Placement compares its existing placement-error types by instance, excluding internal errors of one rigid footprint; thermal/island findings are evaluated because they depend on surrounding zones, not only that footprint. Routing's existing immutable/type exclusions otherwise stay unchanged.

    KiCad 10.0.x reports may truncate at 499 clearance findings and 199 findings of other types, across severities (constants and assumption isolated in the helper). Reaching a cap on either side makes that type's difference unknown; it is not reported as an exact added count. A capped evaluated type with errors on either side sets error_gate (or place_error_gate) to unknown, never clean or a passing comparison, even if the visible errors name only pads. Warning-only caps and routing-immutable types remain diagnostic, with evaluated and non-evaluated capped types recorded separately. added_errors, quality's router_errors, and the existing CLI options retain their meanings and type-count display, now backed by instance differences.

    Connectivity limitation. Completion deliberately retains the existing ratio from KiCad's unconnected_items list. That list may truncate at 499; connectivity_capped discloses this independently of evaluated error caps. The ratio is not an exact connectivity measurement at saturation. No uncapped connectivity worker or new completion definition is included here.

    5. Gates (used by the roadmap)¶

    1. No board in quick gets worse in clean pass or completion (compare_runs.py).
    2. Zero added KiCad DRC errors on every board that was clean before (compare_runs.py).
    3. Time within budget on every board (with --work, the budget is work units; wall time only stops the job).
    4. Routed boards byte-identical unless the change is meant to change results (compare_runs.py --expect-identical; then the differences are recorded).
    5. Quality is judged at equal work, speed at equal wall time. The work budget charges search expansions and flood cells only (the work profile shows what else a run did), so a change that moves work into dearer operations, such as reaching negotiation sooner, takes longer at the same work while routing more in the same time (doc 05 §37). A claim that a change is faster or slower needs runs at equal wall time; compare_runs.py points at the boards.

    6. Implementation status (2026-10-02; sets, work budgets and refill 2026-10-08, D81)¶

    • bench/run.py samples PCBench boards per Freerouting tier, routes each with a binary snapshot, judges with kicad-cli pcb drc, and compares with Freerouting's published per-board results (benchmarks.json).
    • Samples: tier A 40 of 453 boards, tier B 40 of 560, tier C 30 of 122, tier D all 22 (seed 1).
    • Added errors compare physical instances involving a track, via or arc (decision A16), plus error-severity thermal/island findings after refill (D106); other new pad-only reports remain diagnostics. Evaluated capped error reports are unknown, not clean.
    • Results go to bench/results/<run>/ and the progress site's benchmark panel.
    • Latest (final8): tier A 100% clean, B 65.0%, C 56.7%, D 50.0% (Freerouting 2.5.0-RC12: 100%, 50.0%, 46.7%, 36.4%); no router-introduced DRC errors on any board.
    • Sets, --work, --refill and compare_runs.py (D81), measured on origin/main a5532a9:
    • --set quick --work 1000000 --route-args "--variants 1" reproduces the earlier quick-tier run (made with TM_ROUTE_ARGS) byte for byte on all 30 boards: 40.0 % clean, 89.2 % completion, about 30 s with --jobs 4.
    • --set mid --work 20000000: 0 of 11 clean, 76.4 % completion, 3 minutes with --jobs 4.
    • --set planes --work 3000000 --refill --route-args=--soft-zones: 86.1 % completion. Without --refill the judge reads the stale fills, and without the copied project files KiCad judged demo outputs on default rules (hundreds of false track_width and clearance errors on RoyalBlue, StickHub and plane_smd).
    • Timing (D86). The summary's seconds used to be the winning variant's own time. With --work every board runs all eight variants, and at one thread per board (the old default) they ran one after another, so a board's job took several times the reported figure (more than eight times when the winner is one of the quicker variants): on the mid set at 20 M, 6–16 s reported against 45–107 s of process time. seconds now covers the whole job, variant_seconds keeps the winner's time and variants lists every variant. A per-variant profile (decelerator4030, LimeSDR, logicbone at 5 M and 20 M) put 81–89 % of the process in the seven losing variants and under 2 % in reading, set-up, clean-up and writing. Times in runs made before D86, including the Freerouting comparisons, are the winner's only.
    • Work profile and route CPU time (D88). The counters change no output (quick 30/30 byte-identical) and cost no measurable time. Two mid runs at 20 M (--jobs 4 --threads 3, the same work), origin/main against D87 (#21): the four byte-identical boards moved +9 % to +14 % in CPU time between the runs (noise of one sequential pair on this 14-core Mac, or a slow-down that left their output alone: one pair cannot tell); only sbc (+41 %) and kitspace_d20 (+24 %) moved beyond it. A 10 % threshold alone would have flagged seven boards. Single CPU-time comparisons of under about 15 % are not evidence here.

    7. tscircuit BGA breakouts: sets srj19 and srj20 (D90, measured 2026-10-11)¶

    The dense-package work (M9) had no public reference figure. tscircuit publishes 400 synthetic BGA breakout problems in Simple Route JSON and a dashboard with its own router's results on them, so these two sets give one. The format support is doc 08 §9.

    Data. Fetched into bench/data/tscircuit/ at pinned commits by scripts/fetch_fixtures.sh tscircuit, never copied into this repository:

    Set Source Commit Licence Problems
    srj19 github.com/tscircuit/dataset-srj19 (BGA breakouts with passive components on the other side) c1206f3 MIT 200, two layers, 11–87 connections (7,395), 0.15 mm traces, vias 0.3 / 0.2 mm
    srj20 github.com/tscircuit/dataset-srj20 (BGAs with missing balls) 9384fb8 none stated (no licence file, none in package.json): local benchmarking only 200, two layers, 11–108 connections (8,715), 0.12 mm traces, no via size given

    Both use a 0.8 mm ball pitch with 0.36 mm square pads, every connection has two points, and neither states a clearance, a board-edge rule or blind vias.

    Conversion. bench/prepare_srj.py (run by the fetch step once the engine is built) converts every problem with tracemaker srj-import --clearance-mm 0.1 --hole-to-hole-mm 0.1 into bench/data/tscircuit/boards/<set>/<sample>/unrouted.kicad_pcb with its project. The two distances are those of tscircuit's published pass criterion (below), so KiCad's judge and theirs test the same thing; the importer's own default (0.15 mm, tscircuit's router fallback, and no hole rule) is reported as a variant. Via size for srj20 is tscircuit's fallback (0.3 / 0.15 mm). The script checks every board by counting: connections in the problem = ratsnest the board implies = connections tracemaker route reports. All 400 convert and all 400 pass. bench/sets/srj19.txt and srj20.txt name the fixture directory in a #fixtures: line, which bench/run.py now reads, so the sets run by name.

    Judges. The primary judge is KiCad's DRC with the board's rules; a board is a clean pass when nothing is unconnected, no evaluated error instance was added, and no evaluated error type is capped (D106). The second score is tscircuit's own. bench/srj_score.py exports every routed board with tracemaker srj-export and runs tscircuit's evaluateRelaxedDrc on it: the function behind the "relaxed DRC" column of its dashboard, from tscircuit-autorouter 5bcf774 (lib/testing/) with @tscircuit/checks 0.0.233, called as its benchmark calls it (scripts/benchmark/benchmark-run-task.ts): 0.1 mm between copper of different nets, 0.1 mm between via holes (same net included), traces continuous and inside the board. scripts/fetch_fixtures.sh tscircuit-checker installs it (node, packages pinned to the versions that repository names). A board passes when every connection is routed and the checker reports nothing. The checker was not re-implemented.

    tscircuit's dashboard counts boards: "completed" is the share of problems its router solved outright, comparable with fully routed below and not with mean completion; "relaxed DRC pass" is the share solved with no checker error. Its figures, read on 2026-10-10 for its router at 1× effort: srj19 91.5 % completed, 89.5 % passing; srj20 77 % and 77 %. They were not reproduced here: tscircuit's router was not run on this machine, and its run time per problem is not known to us.

    10. Advice (M16, doc 17 §8)¶

    bench/advice_eval.py --set SET --name RUN --work W --variants V --advisor CMD [--half even|odd|all] routes each board with route --advisor CMD: a plain portfolio, then, if connections are left, the advisor and a portfolio with its advice (the unadvised variants again plus advised ones); the better result stands. bench/results/RUN/advice.json has one row per board (connections routed by the plain run, by the advised run, whether it was kept, the best advised variant) and a summary; the stuck report and advice of each board are stored beside it, so a result can be reproduced with route --advice FILE. The gate of issue #26 stage 2 is read on the odd half of a set, the even half being where an advisor is tuned.

    11.1 What PCBWorld-Bench's "679 real boards" are¶

    Doc 18 (A1) took PCBWorld's D3 for an independent second corpus of real boards. Reading the paper (arXiv 2607.05915, the PDF is in the repository clone) and its data tools shows it is not: D3 is derived from PCBench, the corpus this repository already benchmarks. The authors convert PCBench boards to KiCad 9 (design rules kept, then drc_fix_v9.py lowers severities to ignore and a few rule floors to 0), keep the 679 whose converted human layout is fully connected and has no violation, build a "guide board" with one uniform width per net, and split the pool by pad count into D3-A (100 smallest boards), D3-B (287) and D3-C (292). Their evaluation uses fixed test lists (configs/datasets/d3.json): 99 D3-A boards, 10 D3-B, 10 D3-C, and publishes results for D3-A and D3-B only (D3-C is "reserved for future research"). All 119 test boards are PCBench fixtures here by name (bench/sets/pcbworld-d3-test.txt). The PCBWorld repository holds no boards and its conversion needs a KiCad 9 pcbnew built from their engine; that conversion was not reproduced.

    What D3 gives, then, is a fixed, published, pad-count-ordered subset with published baselines, not new boards.
