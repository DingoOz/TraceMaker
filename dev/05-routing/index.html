    05 — Routing¶

    Part of the TraceMaker plan. Start at ../PLAN.md. The stage list, cost formulas and acceptance rules of ../cpp_autorouter_clean_sheet.md §5 are adopted as written unless this document changes them. Read that document's §2 for the evidence (PathFinder, FGR, BoxRouter, AIR, TritonRoute-WXL, Contour, B-Escape, Yan & Wong, Lin et al.).

    1. Principles¶

    1. Optimal search first. Every single-connection search is an A* (or bidirectional A*) with an admissible, consistent heuristic, so it returns the minimum-cost path under the current cost model. What is not optimal is the joint problem; negotiation and learning (doc 06) close that gap.
    2. Escalate on failure, never repeat blindly. Each connection climbs an escalation ladder (§6). Each failed rung writes a failure record. The next attempt reads them.
    3. Proofs, not timeouts, drive the expensive steps. A placement ECO or a "placement-limited" verdict requires a proof that a cut is over-full or a window is infeasible.
    4. Octilinear, not Manhattan. OrthoRoute (GPU PathFinder on a Manhattan H/V layer-pair lattice) is fast on regular backplanes but reaches only ~1–2% clean pass on mixed boards in PCBWorld. TraceMaker routes 0/45/90° on every layer, with only a soft preferred-direction cost.
    5. The KiCad DRC is the judge. Geometry is generated with the compiled KiCad rules and checked exactly before commit.

    2. Representation for detailed routing (revision of clean-sheet §4.3/§5.4)¶

    The clean-sheet design proposed a gridless corner-stitched tile-plane search. This plan changes the order of implementation:

    Phase Search space Why
    First Fine octilinear lattice + exact validation + gridless cleanup. Per layer and clearance class, a bit-packed grid at pitch p = gcd-friendly fraction of (width + clearance), typically 25–50 µm, plus pin-access points off-lattice at every pad (TritonRoute-style). Obstacles are rasterised conservatively from exact geometry bloated by width/2 + clearance. Simple to make correct, maps onto GPU fields, deterministic, memory is abundant (a 300 × 300 mm, 12-layer board at 25 µm is 1.7 G cells = 216 MB as 1 bit/cell/class)
    Later (portfolio arm) Gridless tile plane (Contour-style corner stitching) Better on irregular fine-pitch geometry; added once the lattice router is benchmarked

    Conservative rasterisation can only make the router miss tight gaps, never create violations; the cleanup stage (§8) recovers the gaps gridlessly, and the last-gasp stage retries at half pitch in a window. Every committed segment is validated by exact integer geometry against the R-tree before commit.

    3. Escape (fanout) planning¶

    As clean-sheet §5.2 (min-cost flow with diagonal capacity, Yan & Wong; layer/order from Ozdal & Wong and Lin et al.; negotiated fallback). Additions: - Escape templates from the knowledge base (doc 06 tier 3): a successful escape pattern for a footprint geometry + rule class is reused as the first candidate on later boards. - Escape solving for each dense part is independent → run in parallel. - Built so far: version 1, reserved corridors (§12); version 2, the min-cost-flow channel and layer assignment above for deep arrays, opt-in (§14). The negotiated-congestion fallback is not built.

    4. Global routing¶

    As clean-sheet §5.3, with: - 3-D tile graph with tile ≈ 8–10 track pitches; capacity per edge from the free cross-section after pads and keepouts (exact, from the R-tree), via capacity per tile. - Steiner topology: rectilinear Steiner trees from FLUTE (Flute3, BSD-3, as in OpenROAD stt), adjusted for 45° segments; re-derived when pins merge. GeoSteiner is not used (CC BY-NC licence). - GPU acceleration (doc 07): pattern routing (L/Z shapes, all layers) for all two-pin connections in one batch, then GPU sweep-based maze routing (GAMER-style) for the overflowed ones, in batches of connections whose bounding boxes do not overlap. CPU A* is the reference and the fallback. - Output: corridors, preferred via tiles, and an overflow map written into the history map h.

    5. Detailed routing¶

    5.1 Cost of a step on layer L¶

    cost = len · (1 + w_dir·[against preferred direction]) · (1 + w_h · h(tile)) · corridor_factor
     + bend_cost(angle)            // 45° turn cheap, 90° dearer, 135° forbidden by default
     + via_cost(type, span)        // per via type; micro/blind cost from the stackup
     + present_conflict(owner)     // only when rip-up is allowed: crossing foreign copper
     + learned_penalty(cell)       // targeted history from failure records (doc 06 §3.2)

    All costs are integer fixed-point (int64), so A* is exact and GPU/CPU agree bit for bit.

    5.2 Search¶

    • Bidirectional A* with the GPU cost-to-go field as the heuristic when the window is large: the GPU computes an exact lower-bound distance field from the target (multi-layer, via-aware, ignoring rippable copper) by parallel Bellman-Ford/sweeps over the window. The field is an admissible heuristic that is far tighter than octile distance, so A* expands little beyond the optimal path. Small windows use the octile + via lookahead table (VPR map lookahead).
    • Multiple non-dominated labels per (cell, direction) where the bend cost makes arrival direction matter (state = cell × incoming direction × layer).
    • Priority queue: radix heap (monotone integer keys) — O(1) amortised push, cheap pops.
    • Visited sets: generation-stamped dense arrays per window (no clearing cost between searches).

    5.3 Parallelism¶

    Connections whose search windows do not intersect are routed in parallel on the CPU pool; the scheduler picks windows in a deterministic order. Each search writes into a private transaction; the results commit in id order.

    5.4 Insertion¶

    Lattice path → octilinear segments (merge collinear runs) → snap to pad access points → exact clearance check (both sides of every new pair) → transaction commit. Track widths: net-class width; neckdown only inside pad escape regions and never below the board minimum or the narrowest declared width.

    6. The escalation ladder (per connection)¶

    Each rung is tried only if the failure memory does not already hold a nogood for this connection's current region signature at this rung (doc 06 §3.3).

    Rung Attempt Optimality On failure, record
    R0 A* in the global corridor, no rip-up Optimal in corridor blocking objects on the frontier boundary
    R1 A* in the bounding box ×3 (grown on contact), no rip-up Optimal in box same, plus closest approach
    R2 Negotiated rip-up search: foreign unfixed copper is crossable at present_conflict cost; victims rerouted (clean-sheet §5.6 step 2) Optimal for the cost victim set, victims that failed
    R3 Repair window: rip everything foreign in bbox + 4 / + 12 pitches; reroute under several orders in sibling transactions — orders tried, residual conflicts
    R4 Exact window solve: multi-commodity flow ILP on the window lattice at 2× coarser pitch (CP-SAT), with boundary terminals fixed Proved feasible or infeasible infeasibility core: the minimal set of nets whose boundary terminals conflict
    R5 Trial ordering of the remaining connections (B-Escape): commit the one that traps the fewest others — trap counts
    R6 Cut-capacity proof (Maley): find the over-full cut on every layer Proof cut geometry + deficit → placement ECO request (doc 04 §4)
    R7 Mark placement-limited (if ECO is not allowed or failed) and report — final reason

    The ladder is per connection but with memory: a connection that failed R0–R2 on the last iteration starts at R2 next time unless the region signature changed.

    7. Negotiated repair¶

    As clean-sheet §5.5 (aggressor/victim queue, shifted clip windows, reroute caps, failure predictor), with the DRC markers coming from the own DRC (doc 03 §6) after each batch. History updates go to the shared history map and the failure memory's conflict graph.

    8. Cleanup¶

    As clean-sheet §5.7: pull-tight, via minimisation by layer reassignment, 45° smoothing, corner reduction, optional arcs. Each pass is a transaction with work budgets. Also: teardrops only if the project enables them (KiCad 8+ generates teardrops itself; TraceMaker leaves them to KiCad by default).

    12. Escape planning, version 1 (M9, 2026-10-04)¶

    What failed. On the 17 PCBench boards with BGAs and other dense packages (bga-base, 41 % clean), most unrouted connections were pins reported "boxed in". Two different causes hide behind that word:

    1. Infeasible under the fixture's rules. PCBench ships boards without their .kicad_pro, so KiCad's defaults apply (track 0.25 mm, clearance 0.2 mm, via 0.8/0.4 mm), and old boards keep a large pad_to_mask_clearance with untented vias. The designers' own routed boards (raw.kicad_pcb) fail KiCad's DRC under these rules by hundreds of errors on OtterCast (clearance, track width, via diameter) and decelerator4030 (clearance). No router can route those pins cleanly; Freerouting fails the same boards.
    2. Feasible but taken. On large boards (logicbone: 1,188 connections, 0.035 mm lattice) the strict first pass alone uses the whole 120 s budget; pins whose escape channel another net took first stay boxed in because negotiation never starts.

    What was built.

    Part What Result
    Escape corridors (--escape-plan; on in two of the eight portfolio variants, D33) Dense packages (≥ 8 copper pads, pin pitch ≤ 1.3 mm): perimeter pins get a corridor straight out of the package (2 mm past the pad edge; 0.5 / 1 / 2 / 3 mm gave logicbone 961 / 964 / 968 / 977 and decelerator 449 / 479 / 491 / 490 at a fixed budget); inner SMD balls get a dog-bone corridor to the diagonal via site pointing away from the package centre, reserved only where that net's via fits. Band ≤ ½ pitch (≤ 0.35 pitch for dog-bones) so neighbouring corridors never overlap. Other nets may not enter a corridor in strict searches and pay 2× the crossing cost in negotiated ones; a corridor is released when its pin is connected and planned again on every restart. Reservations only remove options, so they cannot create violations logicbone (one variant, 160 M expansions): 938 → 964 routed, boxed-in 152 → 116; decelerator (200 M): 446 → 454. All 8 variants on, 120 s: BGA set 6,916 → 6,947 routed, tier B 5,163 → 5,171, tier C 9,521 → 9,514, tier A unchanged (100 %), clean pass unchanged everywhere, no added errors.     14. Escape planning, version 2: min-cost-flow channels and layers (M9, 2026-10-05)¶

    Formulation (route/escape_flow.{hpp,cpp}, --escape-flow, off by default; D49). Only deep arrays are planned this way: SMD pads of one footprint on a square grid (≥ 80 % of the balls within pitch/8 of one grid, which tolerates a few test or mounting pads; ≥ 5 × 5 points, ≥ 30 % populated, pads larger than the pitch left to the fixed-copper checks) with a pin to route in the third ring or deeper. Every other dense package keeps version 1's corridors (§12), so with no deep array the plan is version 1's exactly.

    1. Pad layer (Yan & Wong, DAC 2009, network-flow escape model with diagonal capacities). Nodes are the square gaps between four balls (split into in/out with the gap's capacity), arcs join neighbouring gaps through the channel between two balls. Channel capacity = how many tracks fit: k tracks need k·w + (k + 1)·s of free gap, w and s the most common class width and clearance among the array's pins (ties: the smaller), gap = pitch minus the two pad half-extents across the channel. Gap capacity = the same count across the narrower diagonal (√2·pitch, integer square root, minus both pads' diagonal radii); every track turning in or crossing a gap passes a diagonal, and taking the narrower one for all is conservative. A missing ball counts as a point obstacle. Each channel midpoint and gap centre is also checked against fixed copper with the router's own legality test (fixed_code at the planning width) and gets capacity 0 if blocked (thermal pads, planes, keep-outs). Every ball to route is a unit source joined to its four gaps; gaps outside the array are the sink. Min-cost max flow by successive shortest paths (Dijkstra on reduced costs; integer costs 7 per half diagonal, 10 per channel step, 5 straight out of a perimeter ball), so as many balls as possible escape without a via, by the shortest channel sequences.
    2. Via sites (dog-bones): the balls left get one of their four interstitial sites by a second min-cost flow (one via per site; only sites no pad-layer escape crosses, where the via clears the four balls by the clearance and that net's via passes the fixed-copper check; cost 0 for the site pointing away from the package centre, 1 sideways, 2 inwards).
    3. Further layers, nearest to the pad layer first (the layer-by-layer assignment of Ozdal & Wong, TCAD 2006, and Lin et al., DAC 2021): the same flow model on a grid shifted by half a pitch, where the obstacles are the planned vias (all of them: through vias) and the nodes are the gaps between via sites. Balls that escape there are assigned that layer; the others try the next layer.

    Flow paths are decomposed in source order with arcs in fixed order; escapes sharing a channel are placed side by side at the track pitch around the centre of the free gap. The corridor of a pin is its dog-bone (if any) plus the channel polyline (gap centres and channel points) on its layer, extended 2 mm past the array, reserved exactly as version 1's (blocked for other nets in strict searches, 2× crossing cost in negotiated ones, released when the pin connects, re-planned on restarts). Reservations only remove options; every commit is still checked exactly. tracemaker escape <board> --flow prints the assignment per ring (pad layer / via + other layer / via only / none) and per layer; route --escape-report reports per ring how many deep-array pins were connected.

    What the plan finds on the BGA set (escape --flow, the boards' own rules): 8 of the 17 boards have no deep array (LimeSDR_Sony's BGA-named part is too small to be one; EEZ, d20, VESC, red-scout have none); OtterCast's array has no channel and no via site under the fixture rules (rings 2–6: 0 of 42 balls); PocketBone (×3) and DoroidOscillo escape every ball on the pad layer; decelerator needs vias from ring 2; logicbone (2 layers) puts rings 1–2 and 62 of 92 ring-3 balls on F.Cu and 74 on B.Cu, but 130 balls of rings 3–10 get a via site with no room left on B.Cu between the vias; sbc and Own-Mailbox's DRAM have no via site for most inner balls (the solder-mask rule, §12).

    19. Global router v2 and the close of M6 (2026-10-06)¶

    Built (route/global_router.cpp). On top of §16's cut capacities: connections of one net share tile edges (an edge carries a net once, and a connection pays no congestion on an edge its net already holds, so a net's connections merge into a tree with shared trunks: the demand side of a Steiner topology; the tree's pad pairs still come from the detailed router's spanning tree); a via capacity per tile (free sites of the smallest class via on a grid of via pitches, at most 8 × 8 a tile) with its own overflow and history; corridors on the layers a path uses instead of whole via columns; integer costs (256 per tile step), ties broken by node index. Test global_route: --global and --global-congestion are repeatable byte for byte.

    Result. 18 hard boards, one variant, 100 M expansions, connections routed:

    13,305 12,967 12,735 13,324

    Why there is no GPU global router.     M6 gate.     20. Escalation rungs R4–R6 (M8, 2026-10-06)¶

    R6, cut proofs: built (route --cut-report; CutLine in route/global_router.hpp). Every straight line across the board at the capacity samples (eight per tile boundary, both axes) gets a capacity, the tracks that fit across it on all layers past the fixed copper, and a demand, the nets that must cross it. A net counts when one of its planned connections has its two end pads wholly on opposite sides of the line and no pad of the net lies across the line (such a pad carries the net over without a track). Capacity is an upper bound (a narrow probe, the smallest class pitch, free runs counted generously), demand a lower bound, so demand > capacity proves that the placement cannot be routed whatever the router does; the line and the deficit are the request to the placer (doc 04 §4). The first version counted nets by pad centres and "proved" MicroMaple unroutable across a line through its edge connector's pads; the pad-box rule above removed that.

    On the 92 boards of tiers B–D: no line is over-full. The tightest line carries 9 % of its capacity at the median, 12 % on the non-clean boards, 40 % at most. With §16 (tile congestion) and §19 (corridors) this is the third measurement that says these boards are not short of space at board scale: what fails is the fan-out at a package. The report is therefore off by default and costs the global router's set-up when asked for.

    R4, exact window solve: not built. The design called for a multi-commodity-flow model in CP-SAT, which is not available here (no OR-tools C++ library). Its cheaper stand-in, the group re-route of §17 (up to five connections, every order), changed no board's result, and the cut and congestion measurements above say an exact window model would mostly return "feasible, the heuristic just did not find it" on fan-outs it cannot represent at 2× pitch.

    R5, trial ordering: not built. Ordering the last connections by how many others each traps is what the group re-route explored exhaustively on small groups, without effect (§17).

    21. Micro vias (M12, 2026-10-06)¶

    --micro-vias (off): on boards whose rules allow micro vias and with more than two copper layers, a layer change between an outer layer and the layer next to it may use a micro via of the net class's size (uvia_diameter, uvia_drill, not below the board minimums) where a through via is blocked. The search tries it before a blind/buried via; the commit keeps a through via wherever one is legal, so micro vias appear only where they are needed; the exact check uses the micro via's own size over its two layers. No fixture allows micro vias on more than two layers; on two four-layer boards with the setting switched on (EUC-VESC BJT, stm32f407riser; 20 M expansions) routing was complete or unchanged, KiCad reported no error on routed copper, and no micro via was needed. Like blind vias (§11): correct, no measurable gain on the boards at hand.

    22. Successive halving for the portfolio (M10, 2026-10-06)¶

    --halving (off): with more variants than threads, every variant runs on a small budget, the better half runs again on twice as much, until as many are left as there are threads (Jamieson and Talwalkar, AISTATS 2016). Each rung gets an equal share of the thread-time that threads variants would have used, so total work is the same. A router run cannot be resumed, so every rung starts its variants from scratch; the best result of any rung is returned, and the selection is deterministic with a work budget.

    24 hard and nearly clean boards, 30 M expansions per thread, connections routed:

    Threads The first variants, whole budget All eight, successive halving
    2 12,402 12,385
    4 12,508 12,451

    Halving loses a little: its finalists run on a third (two threads) or half (four) of the budget, and choosing among eight variants does not make up for that. With eight or more threads there is nothing to allocate. It would need resumable runs to pay; kept off (D59). The knowledge base's variant choice (doc 06 T3) remains the way fewer threads pick their variants.

    24. Differential pairs: twists, per-pair skew, and what the failures are (M12, 2026-10-06)¶

    Why pairs stay uncoupled (TM_DEBUG_PAIRS now tags each attempt; 18 boards, 59 pairs, first attempts): 63 of 120 attempts couple. Of the failures, 26 are tagged "pin order mirrored between the ends" and 8 "an end pad already carries routed copper"; but 20 of the 26 are one pair (OtterPillG's USB pair, from a bottom-side connector with no via site) tried again and again, and pairs that join routed copper mostly succeed (13 couple, 8 do not). 24 of the 59 pairs have a half with more than two pads. So neither situation is the large class the earlier note assumed.

    Twists (on with pair routing; --no-pair-twists). A new move of the coupled search (kTwist): the right half changes layer first, the halves cross while they are on different layers, the left half changes layer last, and the search continues on the new layer with the sides swapped. In the pair's frame, with D = offset + via offset: right half (0, −off) → via (hj, −vo) → (hj + D/2, −vo) → (hj + 3D/2, +off); left half (0, +off) → (hj + D/2, +off) → (hj + 3D/2, −vo) → via (hj + 2D, −vo) → (2hj + 2D, −off). Each track keeps at least D from the other half's via, which is the distance the coupled via pair keeps; both halves get one via and the same length. Every segment and via is checked exactly, and the finished pair is verified like any other. It costs a via pair plus its uncoupled length, so the search uses it only where the pin order asks for it.

    18 boards, 59 pairs, 30 M expansions: one pair gains coupling (USB-C-Screen-Adapter L3: 0 → 86 %), none loses; pairs at ≥ 80 % 18 → 19, at ≥ 50 % 35 → 36, median share 57 → 63 %; connections routed 2,210 → 2,212. The diff_pair test is unchanged (five pairs 91–94 % coupled, KiCad-clean).

    Per-pair skew limits. RouterOptions::pair_net_skew gives each pair of pair_nets its own limit; pairs found by the component rules take USB2-02's max_intra_skew_mm (1.27 mm). A custom skew rule of the board wins, then the pair's own limit, then --pair-skew-mm.

    Still not built: a pair ending on routed copper as such (the pair's ends are pads; the count above says it rarely matters), pair-aware global routing, arcs, skew in picoseconds, both halves meandering together.

    26. Plane-aware routing of all-SMD boards (2026-10-07)¶

    The case. Small boards put every part on the outer layers and give whole inner layers to ground and supply planes: no pad touches a plane, every plane pin needs a via, and the planes cover the board. On one such board (a private 6-layer wearable: two GND planes and a supply plane inside, a 0.4 mm-pitch WLP, a 0.5 mm-pitch QFN, a BLE module, a 32 kHz crystal; 167 connections) the router stopped at 94/167 with no via at all:

    1. Zone fills are fixed copper of their net, so a via of another net through a full-board plane was illegal everywhere, and a GND via crossed the supply plane. Rule areas "no tracks, vias allowed" on the plane layers, which keep the planes whole, blocked vias too (D65).
    2. plan drops zone-only clusters, so a plane that no pad touches was never a target and GND pads were wired to each other on the signal layers.
    3. With planes as targets, the cheapest plane connection is a via at the pad centre: about 100 vias landed in pads (0.5 mm vias in 0.25 mm QFN pins and 0402 pads).
    4. An inner WLP ball (0.25 mm lands, 0.15 mm gaps) looks free locally (the diagonal gap fits a track), but every exit ends on another ball, and there is no dog-bone site at 0.4 mm pitch.
    5. The 32 kHz crystal line, routed in shortest-first order and ripped by negotiation, ended 25.7 mm long with four vias.

    What was built (all opt-in except the keep-out fix):

    Part What
    Keep-outs (D65) A rule area blocks tracks if it forbids tracks and vias if it forbids vias. Before, only areas forbidding tracks were read, and they blocked vias too
    --soft-zones (D66) Obstacles skips zone fills in copper_state and fixed_code; KiCad refills around the new copper. plan keeps zone-only clusters of a net that has pads, when their fill is at least 1 mm² (a sliver of a stale fill is no target) and a pad of the net can reach it, and never plans a connection between two zone-only clusters. Teardrops are never targets, and a via joins every same-net plane it passes through (§32)
    --keep-vias-off-pads, --vias-off-pads-below MM (2; D67) A via probe treats single-layer pads narrower than the limit, of any net, as obstacles at net-class clearance, also in the cached fixed_code (net-independent, as the cache needs). Exposed pads still take vias
    --via-in-pad (D68) pad_cells offers the pad centre on every other layer, with the board's minimum via (min_via_diameter, min_through_hole_diameter; no via when they could not be read, with a warning), for inner balls (a round pad with a pad of its footprint one ball pitch away in each direction of the footprint's frame, found once per board) and for pads with no legal own-layer cell. The penalty is four vias at the current via price, charged on either end (src.cost, and on entry to a target cell). One via per pad: a pad whose via another connection placed is not offered again. commit adds the via, checked with the pad exemption
    --first-nets A,B (D69) Connections of the named nets go first in plan's order (after learned priorities) and again after every restart; commit and the via clean-up (lns_vias) do not rip them for other nets

    29. Layer limits: layers without tracks, and dearer layers (issue #6, 2026-10-07)¶

    The problem. On a signal / power / ground / signal stack the router treated all four layers alike and put about a third of its track length on the two plane layers. There was no way to say "keep the planes whole" or "use them only when nothing else works".

    Two options, both off by default (layer names as KiCad writes them, the file's own names, or the user's layer names; an unknown layer or a bad factor stops the run with an error instead of being dropped):

    • --no-tracks-on In1.Cu,In2.Cu: these layers get no new tracks. Vias still pass through them, and a via may still end a connection in the net's own zone fill there, which is how a pad reaches its plane. A pad that exists only on such a layer has no legal exit and stays unrouted (the CLI counts them in a warning).
    • --layer-cost In1.Cu=4,In2.Cu=4: a track on that layer costs that many times its length (1 to 1000). The layer stays available; the search takes it only where the detour on the plain layers would cost more.

    How. A layer without tracks is taken out of every net's allowed-layer mask, the same mask that custom disallow track rules fill (§27), so the A*, the reachability pre-check (§13), the cost-to-go field, pad endpoints and escapes, the coupled-pair search and the escape planners all see one thing. Two additions serve both: a via may land on a layer the net has no tracks on where that cell ends the connection in the net's own zone fill, and commit() rejects any segment on such a layer before the exact check, whatever produced the path. The cost factor multiplies the planar step cost per layer in integer per-mille arithmetic (rule 2). Factors below 1 are refused: the octile and field heuristics are lower bounds only if no track costs less than its length. With both options unset, no cost or test changes, and the output is byte-identical (10 PCBench boards at 5 M work units; the quick tier is unchanged).

    Measured on six four-layer PCBench boards (4 variants, 60 s per board, KiCad as the judge):

    Routed (of 1,078) Boards complete Track on In1/In2 Added DRC errors
    Defaults 1,058 5 2,193 mm of 6,512 (34 %) 0
    --no-tracks-on In1.Cu,In2.Cu 1,038 3 0 mm of 6,467 0

    Limits. - The limits apply to every net. A per-net limit is a KiCad custom disallow track rule (§27). - A dear layer that cannot be avoided makes that search wider: the heuristics measure plain length, so the search first exhausts everything cheaper (a 15-fold expansion count on the test board where every way across costs four times). A field computed with per-layer step costs would remove this; it needs the same change in the CPU reference and the CUDA kernel and is not built. - The global router and the cut report (§16, §20) still count capacity on every layer, so --cut-report may call a board routable that is not once layers are closed. Its proofs of "unroutable" stay valid. - Planes that no pad touches are still not connection targets; only a net whose fill already holds one of its pads gets vias into it. - The Python bindings and the KiCad plugin do not expose the two options yet.

    30. Coupled-pair search: rejected candidates are work (2026-10-08)¶

    Before. A pair attempt (§15) counted only the states it closed. Building and checking the legs of start and goal candidates was free, and the attempt never looked at the work budget or the time limit until it ended. On a board whose fills hug its pads every leg fails, so an attempt checks tens of thousands of candidates at about zero work: stripped CM5 with its fills kept and --diff-pairs ran 1,048 s at --time 900 with 130,247 work units counted, and at --work 20000 it ran 635 s. A sample put 98 % of the time in the start legs' exact checks against fill polygons (17,742 vertices for the largest).

    What was built (D77). Every exact segment check of a leg, legal or not, is a work unit, as is every closed state. The attempt adds its work to the router's total every 64 steps (a step is one candidate or one state) and then checks the budget and the time limit, so a budgeted run stops inside an attempt, deterministically, and a long attempt stops at the time limit instead of finishing first. Nothing is committed before the attempt's goal check, so stopping leaves no partial pair. The attempt's state budget is unchanged and leg checks get no cap of their own: a version that capped them at the state budget lost coupling on three of 18 boards at 30 M, where a pair needs many rejected candidates before its first legal one. RouteResult::pair_work and the route summary's pair_work report the part of the work spent in pair searches.

    32. Plane targets: teardrops, unreachable planes, and planes a via passes through (2026-10-08)¶

    34. The router obeys positional disallow rules (2026-10-08, D82)¶

    Before. disallow track / via rules whose conditions depend on where the item is or what it is (insideArea, intersectsArea, enclosedByArea, courtyard functions, Width, Position_X/Y, footprint properties) were DRC-only (§27, §33).     • RuleEngine::probe_disallowed judges a new track or via the way disallowed judges board items: every custom rule in file order, the last match deciding (so ignore exceptions hold).     • Disallow keywords are compiled to bits. Area and courtyard functions resolve their name patterns once (Condition::bind), and an area's outline box rejects far probes before the exact test: the router asks these functions for every lattice point it visits.

    38. Buses (2026-10-11, D91)¶

    Before. The router knew pairs (§15) and single nets with a length rule, but not a group of nets that belong together: a data or address bus, a parallel display interface. Its members were routed wherever the order put them, each by its own cheapest path, so one took a via its neighbour did not need, one went round the other side of a mounting hole, and their lengths differed by millimetres.

    Status: experimental. The generated bus boards meet their skew limits, but six real boards routed slightly fewer connections with the options on (957 → 952 at 100 M work, 886 → 853 at 20 M), and --buses groups some indexed nets that are not a bus. The options stay opt-in until real boards gain from them.

    What was built (off by default: without the options the output is byte-identical, quick 30/30).

    Part What
    Groups from the command line (route/bus.cpp, bus_from_option) --bus NAME=PATTERN, repeatable. The pattern matches whole net names as KiCad writes them (sheet path included: /D0, /MEM/DQ3). [N-M] or [N..M] is an index range and matches any decimal number in it (/D[0-15], zero-padded indices too); * and ? are KiCad's net-class wildcards; everything else in a pattern with a range is literal (A[[0-15]] for nets named A[0]). A pattern without a range goes to KiCad's net-class matcher unchanged (model::pattern_match: wildcards, or a full regular expression, /SPI_(SCK|MOSI)). Members are ordered by natural sort (D2 before D10); only nets with pads count; fewer than two is an error. A net named by two groups is routed with the first (warning)
    Detection (detect_buses, --buses) Nets whose names differ only in a trailing decimal index of at most four digits (D0, A[3], /MEM/DQ12), four or more of them with pads on the same two components. One stem may give several groups (DQ0-7 to one memory, DQ8-15 to another: STEM(REF-REF)). KiCad's generated names (Net-(…), unconnected-…) and names without a letter are never grouped. A detected group that shares a net with a --bus group is dropped. The groups are listed in the log before routing and in the summary
    Skew limit (bus_rule_skew, app::resolve_buses) A custom skew rule of the board applies to a group when every member matches one (the smallest maximum; RuleEngine::net_constraint, the call the pair code uses), e.g. (rule "bus" (constraint skew (max 0.8mm)) (condition "A.NetClass == 'BUS'")). Rules marked (within_diff_pairs) do not count (the project reader now keeps such bracketed flags in Constraint::items). Otherwise --bus-skew-mm X gives the --bus groups a limit. With neither there is no length matching, only grouping: a limit is never invented, and detected groups get one from rules only
    Bundles and lanes (Router::Impl::order_buses) The connections of a group between the same two components form a bundle (the planner's spanning tree gives a fan-out or a fly-by chain one bundle per component pair). All of a bundle's connections are turned the same way round and ordered along the pad row at one end (the wider of its x and y extents), so neighbouring lanes are neighbouring pins and do not cross. A bundle is routed as one block, lane by lane from one side, at the place the router's order gave its first connection; with --bus-first before everything else (after --first-nets). Restarts keep the blocks together
    Following (route_bus_lane, bus_note) The first lane routed leads: it is an ordinary search. Each later lane is first searched inside a guide around the nearest lane already routed as a lane: cells within reach of that lane's tracks on the same layer, and on every layer around its vias and around the new lane's own pads; everything else is blocked (bus_mode 2 in cell_cost). The reach is the distance between the two lanes' pads (at most 5 mm) plus two track pitches and a via. So the lane runs beside its neighbour and can change layer only where the neighbour did. The search is the router's A* with its exact commit; it is cut off at four expansions per lattice point of the guide (at least 50,000), and a rejected commit is retried twice. The result is kept only if it has the neighbour's layers in the same order and as many vias, and its detour (length beyond the octilinear distance of its pads) exceeds the neighbour's by no more than half the pad distances plus 0.5 mm plus 2 % of the neighbour's length; otherwise it is taken back
    Leaving the bus A lane that cannot be routed that way is routed like any other connection (strict, escapes, neck-down, negotiation), with the guide as a preference only: a quarter pitch per step outside it. If it still has the neighbour's layers and vias it is a lane, and later lanes may follow it (this is how a bundle passes an obstacle on both sides); if not, it has left the bus: it stays routed and is reported, and no lane follows it. No connection stays unrouted for the sake of its group
    Ripping Nets outside the groups never rip a group's copper (as with --first-nets; commit); members rip each other as usual. A lane ripped is no lane any more. The via clean-up (optimize_vias, lns_vias) leaves lanes alone, since removing one member's vias would break the equality; smoothing keeps vias and layers and runs on them
    Length matching (tune_bus_skew) In the clean-up, per group with a limit: the members with every connection routed are measured as KiCad's skew check measures them (track length of the net plus the stackup height of each via between the layers it joins; route/bus.hpp, via_heights, net_via_length), and each one shorter than the longest by more than half the limit gets meanders up to between half the limit below the longest and the longest. It is the length-tuning code (tune_net, §15) with two additions for bus members, both off elsewhere: every track is tried, longest first (the lanes beside a member leave its longest track no room), and the last meander is cut to the length still missing (the fixed heights step by 0.5 mm, too coarse for a 0.5 mm limit). Each meander is checked exactly
    Portfolio Between variants with equal completion the one with fewer connections off their lanes wins, then vias and length as before (0 on both sides without buses)
    Report --json: a buses array, per group name, source, members (net, routed, followed, length_mm, via_length_mm, vias, layers; length_mm includes the vias), routed, followed, left, reference_vias, reference_layers, vias_min/vias_max, length_min_mm/length_max_mm, skew_mm, skew_limit_mm, skew_source, within_skew; and bus_lanes / bus_left, the router's own count of connections routed as lanes and off them. The array is measured on the board as written (route::measure_bus), not taken from the router's book-keeping
    Measurement (tracemaker buses BOARD [--bus …] [--buses] [--bus-skew-mm X] [--json F]) The same numbers for any routed board. A member is routed when all its pads are joined (the router's connectivity). The reference is the via count and layer set most routed members share (the first member's among equals); followed members have exactly that, left are routed otherwise. Length is what KiCad's skew check sums: tracks and arcs, plus per via the stackup between the outermost layers on which a track of the net ends in the via (outer copper in full, inner copper by half, as BOARD_STACKUP::GetLayerDistance; KiCad's default stackup when the board has none; nothing when the project turns "use height for length calculations" off). Skew is the longest minus the shortest routed member. Exit 4 when a group with a limit is over it or not completely routed
    Events (doc 13) bus (name, nets, per bundle), bus_lane (connection, net, leader / followed / left) and bus_skew (skew and limit after tuning)

    Work is counted as for every search (expansions and flood cells of the guided and the ordinary attempts); building a guide and placing meanders are geometry and are not charged, like the pair legs' set-up and the existing tuning. Nothing is random and no hash container is iterated: the same job gives the same bytes at any thread count (bus_route test, 1, 2 and 4 threads).

    39. After-route passes: power widening, style metric, stitching vias (2026-10-11, D92)¶

    Three things that happen after routing has finished. Each is its own small module in src/passes/, attached in app/route_job.cpp after the soft-zone refill repair and before the board is written. All are off by default (the style metric only measures), deterministic, and count their work in exact checks with a budget (--pass-work, default 2 M per pass; wall time does not stop them). The two that change copper do it through the router's own obstacle model (route::Obstacles, the check the router commits with), touch only copper of this run, and are transactions (rule 4): the job counts unconnected items per net with and without the pass's result (after an in-engine refill when fills are soft or vias were added) and drops the result if any net has more than before (per net, so that a connection made in one net cannot hide one broken in another). Without the options the routed board is byte-identical to before.

    Which tracks, and how wide. Nothing is invented: a track is widened only towards a width something stated.

    Source Target Applies to
    Net class (source: "net class") The class's track width (raised to the board minimum) New tracks narrower than that: the router's neck-down (§6, §14), on every net except coupled pairs
    --widen-net PATTERN=WIDTH_MM (repeatable; KiCad wildcards on the net name) The stated width Every new track of the matching nets
    Component rules (--component-rules report, soft or on) The width a width_for_current rule computed (IPC-2221 from the rule's current, or its min_width_mm; doc 15 §16) The nets the rule binds, as synthetic_net_classes gives them: instances at the apply threshold, nets in the Default class only

    The largest stated target of a net counts, and a stated target replaces the class width for that net, also when it is narrower: the pass never widens beyond a stated target. Impedance widths are not targets (a controlled-impedance track must not be wider than computed either), and the halves of coupled pairs (--diff-pairs, USB pairs from component rules) are skipped: they were routed at their pair width on purpose. With --component-rules on the computed widths are already the nets' class widths, so the first row restores whatever the router had to neck.

    Method. Per track, in commit order, nets with a stated target first. The candidates are the goal and seven evenly spaced widths below it, down to (not including) the track's own width, rounded down to a micrometre; the widest whose segment_state is free against everything else is kept and entered in the obstacle model at once, so later tracks are checked against it. "Everything" is what the router checks: other nets' copper at the pair's clearance, holes, the board edge, keep-outs, mask openings, custom rules (positional disallow, a rule's maximum track_width caps the goal), and the neighbours of the net's own pads. No other copper is moved or narrowed in this version, so a track in a tight channel simply stays as it is.

    Junctions.

    • Wide meets narrow. Tracks are stadium shapes: both keep their round caps at the shared end point, the copper stays joined, and the wide cap is part of what the exact check tested. No taper is added.
    • Via. A track that ends on a via of its net (at the via's centre, on a layer the via spans) is widened to the via's diameter at most, so the track never sticks out around the via.
    • Pad. A track that ends inside a pad of its net is widened to the pad's smaller side at most: the neck stays at the pin, as a designer draws it, and the wide copper starts at the first bend or junction away from it. Such a track counts as "at target" in the report when it reaches that size.
    • Locked tracks and every track that was on the board before the run keep their width.

    Report. One log line per widened net and a widen object in the JSON summary: per net the target and its source, tracks below the target, tracks widened, tracks at target, widened length, and the length at each width before and after (before_mm_by_width, after_mm_by_width); in total the checks done and whether the result was kept.

    Limits. One width per track as the router cut it: a long track with one tight spot stays narrow along its whole length (splitting a track at the obstacle is not done). Tracks are not moved to make room. A custom rule's maximum track_width caps what this pass does (RuleEngine::track_width returns it, and the in-engine DRC reports tracks above it); the router itself still routes at the class width where such a rule asks for less. Inner-layer widths from IPC-2221 (wider than outer) are reported by the component rules but the pass uses the one width a net class holds. With --soft-zones the widened tracks are judged like the routing itself, after a refill.

    39.2 Style metric¶

    How tidy the copper is. It only measures: nothing in the router or the clean-up optimises it yet. Counts and angles are integer arithmetic on nanometres (cross and dot products); lengths are each segment's hypot rounded to the nanometre and summed as integers. Nothing depends on the order of the input or on threads, so the numbers are the same at every thread count.

    A connection is copper of one net between two ends; an end is a pad of the net, a junction (three or more track ends, or a track end on the middle of another track) or a loose end. A via with exactly two track ends is passed through. Collinear pieces of one width are joined first (the router commits a straight run as several steps), so a segment is a maximal straight run.

    Measure Definition
    bends, bends_per_connection Direction changes between consecutive segments on one layer (not across a via, not at an arc)
    acute_angles Bends where the two segments enclose less than 90° (the direction turns by more than 90°)
    stair_steps Maximal runs of three or more consecutive segments on one layer, each shorter than four track widths, whose bends turn alternately left and right. A single Z-shaped jog (two short segments) is not one
    short_segments Segments shorter than their own width
    off_angle_segments Segments more than 0.1° away from the eight octilinear directions
    detour_ratio Copper length over the shortest octilinear path between the connection's ends (max + (√2 − 1) · min of the two offsets); per board the two sums are divided (detour_length_mm, detour_octile_mm), closed loops excluded
    long_detours Connections longer than 1.5 times that path
    arcs, vias, segments, connections, length_mm Counts; arcs are measured by their length and not judged for bends or angles

    The patterns follow what tscircuit's open-source linters flag (pcb-trace-linter: segments off the 45° directions; check-ugly-traces: removable jogs and off-angle segments; both MIT). They were read for which patterns to count; no code was taken.

    39.3 Stitching vias (--stitch-vias planes|return|all)¶

    Vias of an existing net, added where they tie that net's copper on two or more layers together. Two uses:

    • Plane stitching (planes): for every net with solid fills on two or more layers, a via at each site of a grid (--stitch-pitch, default 5.08 mm, the catalogue's general_high_speed.stitch_via_within_mm; one grid for the board, anchored half a pitch inside the outline's bounding-box corner) where the via's pad lies wholly inside that net's fill on at least two layers. A site with a via or plated through-hole pad of the net within half a pitch is already tied and gets none.
    • Return-path stitching (return): every via of a signal that needs a reference plane wants a via or plated pad of the plane's net within a distance, centre to centre. Signals come from component rules of kind reference_plane (doc 15 §4; with --component-rules report, soft or on, instances at the apply threshold: the nets of the rule's roles, the plane net from the rule's plane_net, by role or by name, default GND) and from --stitch-return PATTERN=PLANE_NET. The distance is --stitch-distance, else the rule's stitch_via_mm, else the catalogue's 5.08 mm. For a signal via without one, candidate sites on rings around it are tried, nearest first (16 directions, ring spacing half a via, positions on whole micrometres); the first site that passes is used. The same two-layer condition holds: a return via ties planes together, so a board with the plane net on one layer only gets none, and the via is reported as unstitched.

    Which fills. The fills stored in the file may be older than the routing. The pass refills the zones in the engine for the routed board (§36) and places against those; hatched zones are left out (the refill does not redraw them).

    What a site must pass.

    1. The router's exact check for a through via of the net's class size (via_state, 10 µm clearer than the rules ask), against every pad, track, via, hole, board edge, keep-out, mask opening and custom rule. Surface-mount pads of any net, the via's own included, count as obstacles: a stitching via is never a via in pad. Copper text is in the obstacle model as an estimated box per line, not as KiCad's glyphs, so stitching vias keep 0.25 mm more than the clearance from those boxes (a grid via beside the text JTAG_EN on kit-dev-coldfire-xilinx_5213 was 0.139 mm from a glyph where 0.15 mm is required).
    2. Other nets' fills. A through via may pass through another net's plane on a layer in between, as every via on a multilayer board does, but only through the middle of it: the hole a refill will cut (via radius + the largest clearance + 10 µm) plus the zone's minimum width as a web must lie wholly inside the fill, away from every edge of it (outline, other knock-outs, thermal gaps). So the hole cannot cut the fill into islands, sever a spoke or leave a sliver. A fill the via neither clears completely nor sits in the middle of blocks the site, and so does any hatched fill within reach. New vias keep two knock-outs and a web apart, so their holes never merge. The web is the largest minimum width of any zone on the board (at least 0.25 mm): the refill prunes copper narrower than a zone's minimum width, and with a fixed 0.25 mm web a 1.4 mm grid through a plane with a 0.5 mm minimum width left that plane in loose pieces between the holes, which the refill dropped as islands (KiCad: 270 of 495 mm² gone where the 164 holes account for 130; no DRC item, no unconnected item).
    3. After all sites: a second refill with the vias. A via stays only if its own net's fill overlaps it on at least two layers (KiCad joins a via to its net's zone solidly, without thermal relief). If a zone of another net has more pieces than before, the whole pass is withdrawn. A stitched net's own zone may gain a piece: an island the refill used to drop, now tied to its net by a via.
    4. The job's transaction: unconnected items per net after a refill, with and without the vias.

    The vias are written with (free yes), so KiCad keeps their net although no track touches them.

    Report. stitch in the JSON summary and log lines: vias per net and purpose, grid sites (in overlapping fills, already tied, blocked), vias dropped by the second refill, and per signal net its vias and how many have a plane via within the distance before and after.

    The reference_plane rule. crules::evaluate still reports rules of this kind as not applied (the no-split-crossing part needs plane-coverage checks, doc 15 P4). The stitching part is satisfied and measured here, per rule instance, as return_paths rows with source naming the rule and its anchor; it is not fed back into the component-rule report.

    Limits. Through vias only. The containment tests walk every edge of the fill a site lies in (no index), which is the pass's main cost on boards with large fills. Fill outlines contain the zero-width bridges that join holes to the outline (§36), and a site on such a bridge is refused although the copper is solid there. Signal vias in dense areas often have no legal site nearby and stay unstitched. Return-path sites are not chosen for the smallest loop beyond "nearest ring first". The written board keeps its old fills, as with --soft-zones: refill before fabrication output. Every via through another net's plane takes its knock-out out of that plane: at a tight pitch that adds up (a 1 mm grid took 11 % of the +3.3 V plane of kit-dev-coldfire-xilinx_5213), and nothing limits it but the pitch. A stitching via beside a teardrop of another net is legal against the pad and the track; KiCad's refill then cuts the teardrop back around the via (measured on a generated board: no DRC item, the teardrop's fill 6 to 12 % smaller).

    Status of return-path stitching. The explicit form (--stitch-return) is tested like plane stitching. The form driven by reference_plane rules shares all of its placement code, but on real boards it has placed one via so far (see §39.4): treat it as experimental until a board set with unstitched high-speed vias exists.

    40. Dense breakouts: limits, portfolio extras and the experiments that did not help (M14, 2026-10-11, D94, D95)¶

    Measured on tscircuit's BGA breakout sets (doc 10 §8, doc 16 §10); this section records what the router now does and what the hidden options are.

    • Defaults. max_rips_per_connection 40 and max_passes 40 (were 8 and 12): negotiation on a dense breakout ends because a connection reached its rip limit, not because the budget ended. 33 % → 54 % clean on the srj19 gap boards at 50 M work.
    • Budget accounting. --work counts search expansions and reachability flood cells (1:1). On a 60-connection two-layer breakout at 10 M the strict first pass and its floods use all of it (9.5 M of 10 M), so negotiation never runs; read a result at 10 M as "first pass only".
    • Portfolio beyond eight. --variants N (N > 8, up to 64) adds seeded variants: fast bends, jittered order (every fourth shortest-first), via cost × {0.4, 1, 2.5}, crossing cost × {0.5, 1, 2}, escape plan on even indices, --package-pen 3 on odd ones.
    • --package-pen P. Inside the pad box of a footprint with at least 30 SMD pads on one layer, tracks on that layer cost P pitches more per lattice step, so an escape takes a dog-bone via early. srj20 gap, 30 M: 13 → 17 clean of 57 at P = 4, 10 at 8.
    • Hidden experiment options (results in doc 16 §10; none helps): --guide FILE, --guide-pen, --guide-radius (per-connection preferred paths; a hard search inside the guide first, cut off at a few expansions per cell, then the usual search with a mild preference), --layer-assign, --order 3, --lns-open N, --no-strict-first, --max-victims, --soft-growth, --history-weight, --max-rips, --max-passes, --max-restarts, --soft-cost-mm.
    • GPU. The cost-to-go fields give the identical result 1.7× faster for one board alone (35.7 s → 20.7 s, sample 13 at 20 M); with twelve boards routed in parallel they are slower (contention), so the benchmark runs use --no-gpu.
    • --layer-dir-pen P, --layer-dir-swap (D98). Orthogonal steps against the layer's preferred direction (even layers horizontal, odd vertical) cost P pitches; diagonals are free. Automatic (P = 0.3, with --package-pen 3) on a breakout board: two copper layers and at least 70 % of the connections with an end on a ball-grid-like package (at least 30 same-layer SMD pads on at least 5 × 5 distinct positions, 40 % of the grid filled). Negative values mean "automatic at that strength" (the seeded portfolio variants use −0.3, −0.6, −1.01). Elsewhere the penalties cost completion (quick 89.2 → 86.8 %), so they stay off.
    • Portfolio extras (variants 9 and up) now vary the direction strength {0.3, 0.6, 1.0} and swap the directions on every fifth.
    • More hidden options, measured and not useful: --polish F (reserve a budget share for rebuilding the open connections of the best state), --layer-assign-angle, --heuristic-weight above 1 (weighted A*: 4 % clean at 1.5), --lns-open.

    41. Negotiation as transactions, the breakout profile and portfolio rounds (M15, 2026-10-11, D99–D101)¶

    Measured on tscircuit's BGA breakout sets (doc 16 §12). Everything here is automatic on a breakout board (D98: two copper layers, at least 70 % of the connections with an end on a ball-grid-like package) and off elsewhere, so quick and mid are unchanged.

    • Transactions (--txn 1, D99). txn_try runs a negotiated search for a connection with a log of the victims it rips. The victims are then routed again strictly, one after the other (no ripping); the route is kept if no more victims are lost than the route gained (--txn 2: strictly more), or with probability exp(−k/T) for a net loss of k (--txn-temp T, default 1.5 on breakout boards; seeded counter-based draws), else a snapshot of every connection's copper, flags and rip counts is restored (txn_capture/txn_restore) and history keeps what the failed attempt learned. A route without victims is kept at once. Pairs and buses are not run as transactions. Hidden options that did not help: --txn-depth (nested transactions for victims that cannot re-route), --txn-orders (several victim orders), --txn-cap, --txn-cool, --tidy, --stall-passes.
    • Reachability floods and the budget (--reach-check 2, --flood-work-pct 25). A flood cell counts a quarter of an expansion against --work on breakout boards (it costs far less time); elsewhere the charge stays 1:1 (the work-profile identity expansions + flood cells = charged work holds only at 100 %).
    • Fields (--field-prefill 1, --field-cache-mb 512). The fixed-copper cache of a net class is filled for the whole board before its first cost-to-go field (boards up to 4 M lattice cells); a field is then a function of (window, target cells, costs) and is kept; a hit needs byte-identical inputs. Identical copper with and without the cache (test), 38 % less wall time on a transaction run.
    • --breakout-portfolio, --rounds R (D101). See doc 16 §12.
    • Warm start. RouterOptions::warm (the conn_routes of a result) starts a run with those routes in place, matched by the two pads of each connection; negotiation begins at once (no strict first pass).

    41.1 Saved state and resume (D102)¶

    With --round-work/--rounds, --state-out F writes the best routes after each round (text: S rounds routed, then R pad_a pad_b nt nv with its T/V lines); --state-in F loads them as the warm start, so a run that ran out of time continues where it stopped. bench/run.py --resume-run NAME does this per board from bench/results/NAME/boards/<board>.kicad_pcb.state.

    41.2 Clearance continuation (--ramp-from, --state-recheck; D103)¶

    A homotopy on the design rules. --ramp-from C0 --ramp-step S (portfolio with --round-work) first routes under rules whose clearances (every net class and the board minimum) are lowered by c_board - C0, then raises them by S per stage until they are the board's own; each stage runs rounds until the board is complete or --ramp-rounds rounds in a row (default 2) routed no more than the best round of the stage, and hands its routes on as the warm start of the next stage. Only routes that are legal under the next stage's rules are taken over (--state-recheck, implied by the ramp; also usable with --state-in for a state saved under other rules): the saved routes legal against the fixed copper are put in together, their conflicts are collected from the obstacle index's owner lists, and the route with most conflicts is dropped until none is left (greedy vertex cover); each remaining route then passes the strict exact check once more. The last stage always runs under the board's rules, and if time or rounds run out before it a final round with no search budget keeps what is legal, so the output never violates the real rules. A relaxed stage always writes --state-out, the final stage only when it does not lose routes. Stage lines go to stderr (ramp stage k/n (clearance -d mm): r of c routed).

    41.3 Relax, route, legalise (--legalize, --warm-pcb, --relax; D104)¶

    route/legalize.{hpp,cpp}. The lattice router puts every track on a lattice point (0.035 mm for 0.12 mm tracks with 0.1 mm clearance) and cannot move a committed route, so it cannot use the room between tracks that a continuous layout would have; a board that is complete under looser rules usually has the topology of a legal board under the real ones. legalize_routes takes the routes of a warm start and moves their vertices (tracks and vias merged by net and position; ends at the centre of their own pad stay; a via in its own pad stays inside it; the board outline and the trust box of 0.25 mm bound every move) until every pair of copper items of different nets is at least the clearance of their classes apart (track-track and track-via by endpoint-to-segment distances, pads as their bounding rectangles or circles with the four corners against the segments, via-via also by hole gap, fixed tracks and vias of the board as fixed vertices). Each pair that is too close pushes the vertices involved along its normal by the missing distance, weighted as in position-based dynamics; sweeps run until nothing is closer than the rule minus 3 µm or 300 sweeps are done. The warm start then keeps the largest conflict-free subset of the routes that pass the strict exact check, and the portfolio routes the rest.

    • --warm-pcb FILE starts from the tracks and vias of a routed board (nets with one connection take all of theirs); --legalize legalises every warm start (also --state-in and the ramp's stage hand-over); --relax = --ramp-from 0.6 c --ramp-step 0.2 c --ramp-rounds 3 --ramp-cycle 2 --ramp-stall 2 --legalize with --round-work 20000000 --rounds 200 unless given: stage 1 routes under 60 % of the clearance, the solution is legalised to 80 %, routed again for what is missing, legalised to 100 %, and when the real rules stall for two rounds the run goes back two stages and climbs again, returning the best result under the real rules.
    • Vertices end off the lattice and off 45° multiples; track lengths grow by the small moves (at most 0.3 mm). Zones, keep-outs, mounting holes and custom .kicad_dru clearances are not constraints of the legaliser; they are caught by the exact check that follows, which drops the routes involved. A projection step is a heuristic: it can leave pairs too close (3-9 on the hard boards), never an illegal result.
    • Prototype with a linear-programming step (sequential LP with a trust region, HiGHS, minimum total movement, scratchpad only) on the six stuck boards: 071, 039, 104 legal in one or two iterations, 103/048/072 with 3/6/11 pairs left; projection: 071, 104 legal, 039/103/048/072 with 2/5/4/9 left. Both turn a 0.06 mm solution (about 800-1000 pairs too close at 0.10 mm) into one with a handful left.

    42. Reference-return audit of high-speed nets (issue #7, 2026-10-14, D114)¶

    Problem. KiCad's DRC does not know whether a fast trace has continuous copper under it. A dogbone escape punches antipads through the reference pour, a plane can be split, a layer change can come without a nearby stitch: the signal is DRC-clean and its return current still walks around the void, which grows the loop area and raises the inductance. The actionable question is per net: does this trace have copper under it, and if not, how far does the return detour?

    What it is. A read-only pass in the family of --cut-report and escape (src/analysis/return_path.{hpp,cpp}). It adds no copper and changes no file. Off unless nets are selected:

    tracemaker return-paths BOARD --nets 'DDR*,*CLK*' [--netclass NAMES] [--diff-pairs] [--reference-layer PATTERN=LAYER]
                              [--stitch-radius-mm 5] [--warn-detour-mm 2] [--warn-separation-mm 1] [--min-void-mm 0.1] [--sample-mm 0.05]
                              [--refill | --no-refill] [--json FILE] [--strict] [--view [--view-port N]]
tracemaker route BOARD -o OUT --return-paths 'DDR*' [--return-path-classes NAMES] [--return-path-pairs] [--return-path-radius-mm 5]

    route --return-paths audits the board as routed, refilling the zones first (the fills in the file predate the new vias, which have antipads); the report goes to the log and the --json summary (return_paths) and each net's path to the viewer. --strict exits 4 when any net has a warning (thresholds are warnings, not DRC errors). Net selection: KiCad wildcards on net names, net classes, and the halves of differential pairs (route::named_pairs).

    Model. A geometric model, not a field solver (no Palace; no impedance, skew or length matching).

    1. Reference copper. The filled zones of each copper layer (antipads and zone holes are holes in the reference polygon; zones without fills are refilled with the engine's refill, doc 05 §36, and the report says so).
    2. Reference layer. Of the layers adjacent to the signal layer, the one with the most copper under the net's traces (a power plane is a valid reference); --reference-layer forces it per net pattern.
    3. Over copper. The trace is sampled every 0.05 mm; where copper is under it the return is its mirror image. A stretch without copper longer than --min-void-mm is a void; its ends are found to within a micrometre by bisection.
    4. Across a void. The return is the shortest path from the void's entry to its exit that stays on the remaining reference copper: A* over the visibility graph of the region's vertices near the void (Lee and Preparata, 1984), the window growing until a path exists. The detour is that path minus the trace between the same two points (at least 0), the separation the farthest the path gets from the trace. If the copper does not connect the two ends (a split plane) there is no return path on that layer: the void is reported as a split.
    5. Layer changes. At a signal via, the reference nets above and below are the nets of the copper around it (the via's own antipad is a void by design). If they are the same net the return closes through the nearest stitching via or through-hole pad of that net inside --stitch-radius-mm; if they differ, through the nearest capacitor that has a pad on each. Otherwise the change is counted as a missing stitch.
    6. Ends. At a pad the assumed return pad is the nearest pad of the reference net, not one assumed ground ball (the comment on the issue).

    Report (text, JSON, and the return_path viewer message, docs/13): per net the layers and their reference, length, void_crossings, detour_mm, max_separation_mm, splits, missing_stitches, length with no reference layer, and per void, layer change and trace end the numbers behind them. Warnings: detour or separation over the thresholds, a split, a missing stitch, a trace with no reference layer (no zone fill on either adjacent layer).

    Viewer. An overlay (viewer/src/returnpath_draw.ts): the signal in cyan, the return in red shifted a few pixels so the two can be told apart, with arrows (the return flows from the end of the trace back to its start), and for the selected net callouts for the signal pad, the assumed return pad, the signal via, the return via or capacitor (or a missing stitch), and the separation. P toggles the overlay; the side panel lists the audited nets worst first and a click zooms onto one. return-paths --view serves a board and its audit with no router running; route --return-paths --view shows it after the routing.

    Cost. The reference copper of a layer is indexed (src/analysis/region.hpp): edges and vertices in a 1 mm grid, and 0.25 mm rows for the inside test, so a query costs its neighbourhood and not the whole pour (the plane of a large board has hundreds of thousands of edges, mostly antipads). Every indexed query has a linear reference (island_of_linear, crosses_linear, nearest_boundary_distance_linear, vertices_near_linear) and tests/test_return_path.cpp compares them on a pour with antipads, a slot and an island (and on square antipads, where a pad at the centre is exactly as near to four edges: the first edge in the region's order wins in both, so the answer does not depend on the order the grid is walked in). Measured on this machine (one core): the Jetson AGX Thor baseboard demo, 291 nets of *CLK*,*DQ*,*USB*, took 105 s before the index and 9 s after; the 12-layer vme-wren demo, 236 nets, 38 s including the refill of its 123 zones (it did not finish in 8 minutes before); RoyalBlue54L-Feather, 7 nets, 0.5 s (bench/records/issue7/samples/timings.txt). Most of what is left is the shortest paths across many small voids.

    Hooks left, not built. A router cost for crossing a reference void, suggested stitch-via sites, and automatic rerouting: the issue's non-goals.

    Limits. Arc tracks are not analysed (a warning says so). The detour of a trace that starts or ends over a void is measured from the nearest reference copper, not from a modelled return pad. Return current also flows through the plane on both sides of the trace and through other layers; this is the shortest-path estimate on the adjacent one. Where a trace starts or ends over a void (a pad at the centre of an antipad) the return regains copper at the nearest boundary point; when several are exactly as near the first in the region's edge order is taken, and the detour of such an end can change by half a millimetre with that choice (1.6 mm or 2.1 mm for one SWD net of the RoyalBlue demo), so a number near a threshold there is an estimate, not a verdict. Antipad polygons come from the fills as drawn (a 32-gon circle, not a true circle), a few micrometres in a 1 mm antipad. Results on the acceptance picture of the issue (about 4.87 mm separation at a processor dogbone field, about 1.00 mm at the memory) were not reproduced: that board is not here.

    43. Footprint check against datasheet land patterns (issue #5, 2026-10-14, D115)¶

    Problem. A footprint can be DRC-clean and still not be the part's land pattern: a library footprint that is for the wrong package, a pad that was nudged to make a route fit, pins numbered the wrong way, a drill that is too small for the lead. Routing such a board is wasted effort. The issue asks for an option that checks components against their datasheet footprints and calls any discrepancy an error, with a trusted list of datasheet brands.

    What it is, and what it is not. TraceMaker does not read datasheets: a land pattern in a PDF is a drawing, and extracting numbers from it is a job for a person (or a model) whose result must itself be checked. The check works on references: records of a land pattern made from a datasheet, each saying where it came from. A footprint is compared with the reference made for it, and only with a reference whose brand is on the trusted list; a reference from any other source gives no verdict (the footprint is reported untrusted, never as fine). The check verifies a footprint against a record somebody vouched for, it does not vouch for the record. Read-only; nothing is fetched from the network.

    tracemaker footprint-check BOARD --refs DIR_OR_FILE [--trusted-brands FILE | --trust-all] [--only 'U*,J*'] [--require 'U*,J*']
                           [--mpn-field NAMES] [--position-tol-mm 0.05] [--size-tol-mm 0.05] [--drill-tol-mm 0.05]
                           [--all] [--json FILE] [--strict] [--view [--view-port N]]
tracemaker route BOARD -o OUT --footprint-refs DIR_OR_FILE [--footprint-trusted FILE | --footprint-trust-all] [--footprint-require 'U*']
                           [--footprint-tol-mm 0.05] [--footprint-warn-only]

    footprint-check exits 4 when a footprint differs from its datasheet (with --strict also on a warning), 1 when the library cannot be read. route --footprint-refs runs the same check before the first track is routed: a discrepancy is an error and stops the job (exit 1, nothing written) unless --footprint-warn-only; the findings go to the log, the --json summary (footprint_check, only the footprints with something to say) and the viewer.

    References. A directory of JSON files (read in path order) or one file; docs/footprint_refs/example-synthetic.json is a synthetic example of the format (its brand does not exist). Each entry names the brand, the part, the datasheet it was made from (document is required: a record that cannot be traced to a document is not a reference; revision, page, figure and URL are kept and shown in the report), which footprints it is for (match: mpn, lib_id, value, ref, KiCad wildcards, every list given must be satisfied; part numbers and values ignore case) and the pads: inline (number, type smd, thru_hole or np_thru_hole, shape, at, size, angle, drill; millimetres, KiCad's y-down footprint frame) or "footprint": "file.kicad_mod", the manufacturer's own KiCad footprint, read by the engine's board reader (paste and mask apertures are not land pattern and are dropped). A reference may carry its own tolerance_mm. Unknown keys, a missing datasheet, a match that selects nothing and a through hole without a drill are refused: a misspelt tolerance that is silently the default would be a wrong answer from a verification tool.

    Trusted brands. trusted_brands.txt beside the references, or --trusted-brands FILE: one brand per line, Canonical | alias | alias, compared without case, punctuation or corporate suffixes ("Texas Instruments Incorporated" = "TI" if listed so). No list means nothing is trusted and the report says what to do; --trust-all uses every reference and the report says that too. docs/footprint_refs/trusted_brands.txt is a starting point to copy and edit, not something the tool applies by itself: whose datasheets to believe is the user's decision.

    Finding the reference. For each footprint with pads and a designator: the references whose match it satisfies, the most specific (most selector kinds) first, then library order; the first whose brand is trusted is used, and when several matched a note says which. The manufacturer part number is read from the footprint's properties named MPN, Manufacturer_Part_Number, Mfr Part Number and the like (--mpn-field adds names). A footprint with no reference is unverified (counted, listed with --all); --require 'U*' makes that an error for those designators. A reference only from untrusted brands gives status untrusted and a warning (an error where required).

    The comparison. The datasheet pattern is laid over the footprint: the library's choice of origin and of orientation is not part of a land pattern, so the alignment is a translation and a rotation by a multiple of 90 degrees, mirrored or not (8 candidates; the translation is the median of the offsets of the pads that share a number, which one or two wrong pads cannot move; the candidate with the most pads paired, then the smallest worst deviation, wins; a pattern that fits several ways because it is symmetric is taken the way that agrees with the footprint's side). A mirror is not free: a footprint on the front must match as drawn, one on the back mirrored (that is what flipping does); a pattern that fits only the other way is the error mirrored, the pin numbers run the wrong way. Then every pad:

    kind an error when
    pad_count, missing_pad, extra_pad the footprint has other pads than the datasheet (an unnumbered non-plated peg the datasheet does not show is a warning)
    position a pad is farther than the tolerance (default 0.05 mm) from where the pattern puts it, after alignment
    size width or height differ by more than the tolerance; a quarter turn of the pad swaps them; custom-shaped pads are not compared
    drill a hole where the datasheet has none or the reverse, or a drill off by more than the tolerance (oval drills compared by their two sides)
    pad_type SMD, plated through hole and non-plated hole differ
    orientation a pad is turned to an angle that is not a quarter turn from the datasheet's (its size cannot be compared)
    pattern no pad number of the footprint is in the datasheet pattern

    Pad shape (rect, roundrect, oval) is not compared, only its extent. With two pads a displacement shows on both by half (the pair's distance is what is wrong).

    Report (text, JSON, the footprint_check viewer message of docs/13): per footprint its status (ok, mismatch, unverified, untrusted), the datasheet it was compared with (brand, part, document, revision, page), the alignment found, and each issue with its pad, a sentence, a few words for the board and where it is. Viewer: a Footprint check panel lists the footprints with findings (errors first) and a click selects one, zooms onto it and lists its messages; rings on the footprints that differ (red) or have an untrusted reference (amber), marks and short labels on the wrong pads of the selected one; D toggles it.

    Checked on real boards (bench/records/issue5/real-boards/). These runs test the alignment, the rotation and the flip, not the datasheets: the references are derived from the boards themselves. (1) On nine KiCad demo boards, a reference taken from the first front instance of every library footprint was compared with every instance on the board: 3,144 footprints, front and back, at every rotation they had, all ok (the back ones aligned mirrored), none called out. (An earlier version of the script derived references from back instances and read oval drills as round; the check rightly reported 'mirrored' and drill errors there, which is what those references said.) (2) On video, CM5_MINIMA_3, vme-wren and the Jetson baseboard, the library footprints that appear on both sides: 2,257 footprints, all ok. (3) A negative control: the same references with one pad moved by 0.2 mm and another widened by 0.3 mm were called out on all 32 footprints they applied to on CM5_MINIMA_3 (61 position and 3 size errors). The check takes about a second on the largest of these boards (1,500 footprints).

    Limits. The references are as good as whoever made them: a typo in a record is a typo in the verdict, and a reference from a trusted brand is only trusted because the list says so. Only copper pads and non-plated holes are compared (not courtyard, silkscreen, paste or mask, not 3D models, not the pin functions of the symbol). Pads of arbitrary angle are not compared by size. Footprints are matched by part number, library id, value or designator, not by reading the datasheet link in a footprint's properties. Nobody has used the check on a board of their own against references made from real datasheets, and no list of references ships with the tool: the example is synthetic.

    44. Critical nets: JLCPCB's three routing rules (issue #24, 2026-10-14, D117)¶

    Problem. JLCPCB's advice on routing is three rules: route the critical signals first, keep vias few, keep a solid reference plane and never cross a split. TraceMaker had the pieces (--first-nets, --via-cost-mm and the via clean-up, return-paths after the route in §42, the component rules' roles in doc 15) but nothing joined them: the user had to name the critical nets, vias cost the same for every net, and the router neither avoided nor reported a track over a plane void. This adds the three rules as options, off by default.

    tracemaker route BOARD -o OUT --si-rules                       # the three rules together, with the settings below
tracemaker route BOARD -o OUT [--critical-auto] [--critical-nets 'CLK*,USB_D*'] [--critical-first]
                              [--critical-via-cost 3] [--critical-via-max 2]
                              [--split-cost 4 | --split-hard]

    Which nets are critical. --critical-nets names them (KiCad wildcards, tier 1). --critical-auto adds the nets that the component rules' roles make critical (doc 15; the table is crules::critical_roles(), every row a role that carries an impedance, differential-pair, length-match or via-limit rule in the catalogue) and the halves of differential pairs (named_pairs, tier 2):

    tier what roles
    1 clocks, crystals, RF lines: the signals that radiate and that nothing may disturb crystal xin/xout, oscillator out, rf_line line, and the clocks of PCIe (refclk), MIPI, DDR3/DDR4 (ck), SDRAM, QSPI, SD/SDIO
    2 high-speed differential links USB 2.0 dp/dm, USB 3 sstx/ssrx, Ethernet mdi_pairs and line_pairs, HDMI/DP tmds, LVDS pairs, MIPI data, PCIe tx/rx, SATA pairs, and named pairs
    3 memory and other fast parallel buses DDR byte lanes and address/command, SDRAM data and address, QSPI data, SD/SDIO bus, Ethernet MAC bus

    The detection runs on the board whatever --component-rules says (it reads, it does not apply rules; a --rules-override file is honoured). The user's --critical-nets are tier 1, like clocks, and win over a role; the log names the nets per tier.

    1. Order (--critical-first). Critical connections are routed before all others, tier by tier, shortest first within a tier, after --first-nets (which stay in front), and again after every restart. Unlike --first-nets this is an order only: other nets may still rip a critical net during negotiation.

    2. Vias (--critical-via-cost F, --critical-via-max N). A via costs a critical net F times as much as --via-cost-mm in every search, the clean-up stages included (their own multiplier compounds), so it takes a longer way on one layer where there is one. --critical-via-max is a report threshold: a critical net with more vias than N is listed with a warning. The vias of each critical net are counted in the report whether or not the option is given.

    3. Plane splits (--split-cost P, --split-hard). route/ref_map.hpp answers, for every cell of the router's lattice on a layer that has a plane next to it, whether the cell's centre is over the plane's copper. The reference of a layer is the adjacent layer whose zone fills cover at least 30 % of the board's bounding box (the larger if both; the fills in the file, refilled by the engine where there are none); a plane layer with no plane beside it (the outer plane of a two-layer board) counts its own gaps, so a net cannot hop onto the plane to cross its slot on the cheap. The fill is rasterised by scanline; tests/test_critical.cpp compares it with a point-in-region scan of the same region, cell by cell. A critical net pays P pitches per lattice step (--split-cost) over a void, or may not enter one (--split-hard: a net with no way round a split stays unrouted, and the report lists it as not routed). It is a cost in the search, not a change to the exact check of a commit. Cells within a critical net's own pad's radius plus 1 mm are never counted (the plane's antipad round a through-hole pad would otherwise close the pad in under --split-hard). Three things make it effective: the smoothing pass (smooth_paths) may not shortcut a critical net over more void than the path it replaces; a critical net whose first path ran over a void, or hopped layers where a dearer via was asked for, is searched again in a 20 mm window (refine_critical; A* is optimal in its window, which contains the first, and the first path is committed as it was if the refined one fails the exact check); and a net with no void on its first path costs nothing extra. Connections that fail never get the wider search: a window that size on a connection that cannot be routed would spend the work budget.

    Report. After the route, for the critical nets: the log (critical nets after the route: N nets, V vias, C plane void crossings and one line per warning), the --json summary (critical_nets: options, per net tier, why, vias and length added, and where the board has a plane the voids it runs over, the detour and the splits from the audit of §42 on the refilled board), a critical_nets event and each net's return_path event for the viewer (doc 09, doc 13). Warnings: a split crossed (no return path on that layer), a void run over, more vias than --critical-via-max. The tiers and the options are on the tui screen with their help text like every route option.

    Off by default. Without these options the route is the run it was: tests/test_critical.cpp and bench/records/issue24/ show byte-identical boards on the quick, planes and planes --soft-zones tiers. --critical-nets alone, with no cost or order, is a report only and also changes nothing about the copper.

    Measured (bench/records/issue24/). Planes tier with --soft-zones, 4 boards with 28 critical nets (by role or pair), 3M work units, one seed; the baseline is --critical-auto alone (the audit on the unchanged copper). Compared on the nets that both runs routed, so that a net one run could not route does not count as having no crossings:

    options critical nets routed connections routed (of 882) common nets vias void crossings splits
    baseline 25 / 28 807
    --critical-first 26 806 23 18 -> 20 62 -> 72 22 -> 23
    --split-cost 4 21 805 21 18 -> 16 57 -> 52 20 -> 11
    --critical-via-cost 3 21 805 21 18 -> 12 57 -> 47 20 -> 11
    --split-cost 4 --critical-via-cost 3 21 805 21 18 -> 14 57 -> 48 20 -> 11
    --critical-first --split-cost 4 25 801 22 17 -> 17 63 -> 68 21 -> 18

    Read as: the split cost and the via cost, without the order, roughly halve the splits crossed (20 -> 11) and cut vias; --critical-first by itself adds crossings, and with it the benefit of the split cost mostly goes (21 -> 18 with the split cost, 26 -> 25 with all three), so --si-rules, which is all three as the issue lists them, is not the best measured combination: --critical-auto --split-cost 4 --critical-via-cost 3 is. Variation between runs is as large as some of these differences: the critical nets that two of the runs fail to route (four USB pairs on StickHub) are also unrouted in a single-variant run of the baseline, so which portfolio variant wins moves the routed counts by a few nets and a few connections, and the clean-pass count (2 of 8) did not move at all.     Five seeds (doc 18 A5, 2026-10-28, D146; bench/records/m21-a5). The same comparison was repeated over seeds 1-5 on a later binary (C5's crowded-source portfolio). No critical-net measure varies with the seed: the differences between the options are systematic. On the nets both runs route:

    • --critical-via-cost 3 cuts their vias by 4 and crossings by 3.
    • --split-cost 4 cuts crossings by 6 and adds 2 vias.
    • Both together cut vias by 2 and crossings by 4.

    The one-seed table's 20 -> 11 splits did not recur. --critical-first routes 27 of the 28 critical nets against 23 to 25 without it (RoyalBlue's crystal net and debugger USB pair are routed only with it). It costs 6 connections of the other nets in every seed, and with it the cost terms change nothing on the common nets. --si-rules keeps all three: its purpose is the critical nets, and the costs alone are still available.

    Limits. The tweet the issue quotes gives no numbers, and none were copied: 3 for the via multiplier and 4 pitches per step for the split cost are the values of --si-rules, chosen on the benchmark runs recorded, not derived. The cost map knows the zone fills of the file, not the antipads of vias the route adds (the audit after the route does, on a refilled board). Only the smoothing pass is made split-aware; the other post-passes (length tuning, pair coupling) are not. A rule's own plane_net parameter (doc 15 USB2-09, ETH-13) is not read: the reference of a layer is the adjacent layer with most copper. A plane that covers under 30 % of the board is not a reference plane. Net classes, via budgets per role and a hard cap on vias were not built (the report threshold is the cap).

    45. Rule relaxation spends nothing on power nets (--no-neck-nets, 2026-10-17, D124)¶

    When a board only routes under looser rules (reports/realworld, the rule-escalation ladder), the relaxation goes to signals. Power and ground nets have the least margin (current, drop), so they keep the board's own values. Two parts: (1) the rule file of a relaxed stage keeps each power net in a copy of its class (<class>_keep) with the board's own clearance and via sizes while the other nets take the tier's values (reports/realworld/py/rules.py: apply(..., keep=power_nets(text)): names such as +3V3, 5V, VBAT, GND, and every net of a class the designer made 0.4 mm wide or more); (2) the router option --no-neck-nets A,B,... (RouterOptions::no_neck_nets) takes those nets out of the escalation ladder's neck-down (the narrower track and the small via the router falls back to when a pad is boxed in): they keep their class width and class via or stay unrouted. Empty by default: no other behaviour changes. Test: tests/test_stall.cpp "no_neck_nets" (a 0.35 mm gap routes only by necking down to 0.15 mm; listed, the net does not route). A relaxed routing is also simulated before it counts: reports/realworld/py/safety.py (crosstalk of every compromised signal pair, IPC-2221 and ngspice DC drop of every narrowed net, via impedance; verdict PASS/WARN/FAIL).

    46. Shove with bending: legalisation that can cut a track (--legalize-subdivide, 2026-10-17, D125)¶

    Problem. legalize_routes (§41.3) moves the vertices a route has. A long straight track has two, both often on pads, so it can only move as a whole or not at all: where an existing neighbour sits too close to its middle, nothing can give, although a kink would. (The case raised by the owner: a via jump needs room that a nearby track could free by bending.)

    What was built. LegalizeOptions::subdivide_mm (router option --legalize-subdivide MM, off by default; with --legalize or --relax). Every unlocked route track is cut into pieces of at most that length before the sweeps, at the vertices of same-net copper that lie on it (a junction or via stays a vertex, so the copper stays joined whichever way the pieces bend) and evenly in between. The projection moves only vertices that are in a violated pair, so the track bends only where it is pinched. After the sweeps a vertex that is within 0.5 um of the line through its kept neighbours (and is not a junction) is merged away, so a track that did not need to bend comes back as the one segment it was. Locked tracks and foreign copper are untouched; every route that is kept still passes the exact check. Test (tests/test_txn.cpp, [legalize]): a straight 10 mm track between two fixed pads with a locked neighbour 0.06 mm from its middle (rule 0.1 mm) cannot be resolved without cutting, resolves with a 1 mm cut (it bends, the pieces that stayed straight merge, the DRC is clean, ends and chain intact, same result twice).

    50. Bundle (river) escapes (2026-10-18, D129)¶

    Before. The router routes one connection at a time, each along its own cheapest path. The sixteen to thirty pins that leave one side of a QFN for one connector therefore take diagonal shortcuts that cut across their neighbours' channels, and the pins behind them are "boxed in": on the EtherCAT shield (LAN9252, QFN-64, 0.5 mm pitch) no run closed fewer than 3 connections, and the designer's own routing, a straight 0.5 mm-pitch comb of 5-19 mm that peels off at the pads of a header 40 mm away, was out of the router's reach: group rerouting in any order (§49) ended at 4-15 open, escape corridors only reserve ground (the net still bends early), and --buses lanes follow a leader that has already bent (§38). Review item 1 of reports/realworld/ethercat_qfn_analysis.md.

    What it is (--bundle-escape, off by default: without it nothing changes; --bundle-min N, default 3; route/bundle.{hpp,cpp}, called from Router::route_bundle_escapes after the escape plan and the coupled pairs, again after every restart). Not a search per connection:

    Step What
    Groups Unrouted two-pad connections with one pad on the perimeter of a dense package (≥ 8 copper pads, pitch ≤ 1.3 mm, SMD, within 3/4 pitch of one side of the pad-centre box; corner pins and thermal pads are not perimeter pins, as in the escape plan) and the other pad on another part, keyed by (package, side it leaves from, other part, side of that part its pad is nearest to (ties: the side facing the package); a header's two columns arrive from their own sides). Fewer than --bundle-min connections: left to the router. Larger groups first.
    Spine One A* for a track as wide as the whole block (lane span + a track width) on an octilinear grid (0.5 mm), from just outside the pad row (the block's round cap clears the pins by one clearance) to the neighbourhood of the front of the destination side. Turns are 45° and at least 2·half-span·tan 22.5° + 2 steps apart so that the inner lanes of a turn keep a positive length; each edge is the router's exact segment check (Obstacles::segment_state, strict) of the wide track, memoised. Cost: length + 6 steps per turn; at most 3 M expansions (geometry, not charged to --work, like the pair legs' set-up).
    Planarity Lanes peel toward their pads, so the lane nearest the pads' side must have the pad that comes first along the lanes' last direction. Pins and pads come in whatever order the netlist gave them; the longest run of lanes that agree (strictly, 0.3 mm apart) is the bundle, the others are left to the router. Fewer than --bundle-min agreeing: no bundle.
    Lanes Lane k is the spine offset by its pin's distance from the middle of the block (rigid offsets, mitred at the corners: the order of the pins is the order of the lanes, so lanes cannot cross), prefixed by the straight run from the pad. It is walked in 0.25 mm pieces while each passes the exact check; the lane peels off at the last place from which a leg to its pad passes: a diagonal then a straight run, or a straight run then a diagonal, no turn over 45° (so lanes hug the block and leave one by one, as in the designer's comb), but never behind the pad. A lane with no such place is left to the router.
    Placing place_bundle_lane checks every piece again with the exact test and adds the tracks as the connection's copper: routed, bus_lane (clean-up leaves it alone) and bundle_lane: no other connection may rip it (commit: "would rip a bundle lane"). A restart rips everything and the bundles are placed again.

    Everything is checked by the router's own exact test before it is committed (rule 1), the order of groups, lanes and searches is fixed (rule 2), a connection without a lane is routed as before, and a lane is a transaction in the sense that a refused lane changes nothing.

    Result. Router's own count on the EtherCAT shield at the board's rules, 20 M work, --soft-zones: base 177/207 routed; escape features alone 179; --bundle-escape 185; with --escape-plan --escape-length 12 189 (30 unrouted -> 18). Eight lanes are placed: five to the right column and three to the left column of P1, straight 0.5 mm-pitch runs for 10-15 mm (render reports/realworld/tmp_img/ec/b_Ba.png). With the designer's own copper as seed the same board stopped at 163-182 (§47 table): the comb alone is not enough; what is left is the top side (the Ethernet pairs and their passives, short connections no bundle covers), the supply pins, and lanes that are not planar on one layer (the designer puts those on the back layer with vias). Tests [bundle] (tests/test_stall.cpp): the pins of one side leave as straight parallel lanes, deterministic and DRC-clean; a pair of crossed pads loses lanes; off by default.

    Not built. A second layer for the lanes that are not planar (pin-to-via drops at 0.5 mm pitch need two staggered rows), merging the lanes of two sides that go to one destination side, bundles to passives (short) and to parts beside the package, a spine that bends round placed bundles' future neighbours.

    53. Generated pours and the layer-count advisor (2026-10-27, D138)¶

    M20's C3 (doc 18 §4). PCBench boards have no zones; §18 measured what leaving the poured nets to a pour could give (4 of 34 boards complete when those nets are skipped) and called creating pours a possible feature. This section builds it, with a way to change the copper layer count and an advisor that tries several counts.

    Pours (route --pour auto|NET@LAYER, repeatable; passes::plan_pours, BoardEditor::add_zone). auto adds one pour, only to a board without copper zones: the ground net by name (crules::ground_like_name; the one with the most pads) on In1.Cu when the board has inner layers, else on B.Cu. NET@LAYER adds that net on that layer. The zone is the outline's box plus 0.5 mm (the fill stops at the board edge), clearance the net class clearance but at least 0.3 mm, minimum width 0.25 mm, islands removed, and solid pad connections (below). A pour turns on soft zones (§36): it is filled before routing so the router sees the plane, other nets route through it, and the refill, the refill repair and the thermal check after routing decide what it connects. The output holds the zone with the engine's last fill; the summary lists each pour (pours: net, layer, reason, clearance, polygons, filled area).

    Layer count (route --copper-layers N; tracemaker layers BOARD --count N -o OUT; BoardEditor::set_copper_layer_count). Inner layers are added after the last inner entry of the layer table, in the file's own numbering (KiCad 9's even ordinals, In1 = 4, or the older In1 = 1, told apart by B.Cu's ordinal) and quoting; through-hole pads take the new layers through their *.Cu. Layers are removed from the top inner one down, and only if nothing names them (tracks, arcs, blind or micro vias, zones, graphics, texts, pads); otherwise the edit is refused and the file is untouched. A stackup block is removed so KiCad builds its default one for the new count. Untouched content stays byte for byte; 2 → 4 → 2 gives the input back (test [layers]).

    Advisor (route --try-layers 2,4,6; app::run_layer_advisor). Each count is routed in turn, fewest first, with the same options; a count the board cannot take (inner layers in use) is recorded as not tried. It stops at the first count the engine judges complete (every connection routed and, with zones, nothing unconnected after the refill) and writes that board; if none completes it writes the count with the fewest open connections (ties to fewer layers). The summary's layers holds the chosen count, whether it completed, and per count the routed and open connections, vias and seconds.

    54. Unfilled zones as planes, and custom hole clearance in the router (2026-10-27, D140)¶

    Found on a 1,194-connection, four-layer WholeBoard board (an eight-port PoE switch: every part on F.Cu, GND zone on In1.Cu, +54V zone on In2.Cu, both written without a fill, JLCPCB rules).

    Unfilled zones. A zone with no filled_polygon gave the router nothing: it neither saw the plane as a target nor kept other nets off it. The plane nets were joined pad to pad by tracks (1,359 mm of GND and 414 mm of +54V on the routed board, some of it on the other net's plane layer), and those 0.8 mm power tracks crowded the escapes of the 0.5 mm-pitch QFN-56 controllers where the last open connections were. The output keeps the zones as they were written; KiCad fills them. Test [pour] ("a zone without a fill is filled for routing").

    Custom hole clearance. The router kept only the board minimum hole clearance (0.2 mm here); custom hole_clearance rules were checked by the DRC but not by the router. JLCPCB's "Hole to copper" (0.254 mm, no condition) was then broken wherever a 0.5 mm neck-down via (0.1 mm annular) sat at the 0.15 mm copper clearance from another net: 14 KiCad hole_clearance errors (0.2395 mm) on the routed board. RuleEngine::router_hole_clearance() is the board minimum raised to every applied custom hole_clearance rule; every router check (route::Obstacles, the lattice margin, stitching reach, pair via spacing) uses it. A rule with a condition or a layer is kept round every hole, which is conservative (rule 6), and a warning says so; the DRC still checks it as written. Test [rules] ("custom hole_clearance rules").

    Not done: rules whose condition uses A.Net (JLCPCB's "Hole to hole" between different nets, 0.5 mm) are still not applied by the router or the DRC (the engine does not evaluate Net); KiCad found no such error on that board.

    56. Pin swap: what the freedom would be worth (M20 C2, 2026-10-27, D141)¶

    bench/pin_swap.py measures an upper bound before any pass is built. Groups of pins are taken as swappable by construction (assumption A73), not from the design: a connector's signal pins (reference J, P, CN, CON or X; one pad type and size; not a supply, ground or differential-pair net; the net's only pad on the connector), standing for a connector wired to interchangeable GPIO, and the resistors of a resistor array (RN/RP, 4, 8 or 16 pads; a resistor moves as a unit, either way round). An oracle assigns the group's nets to its pads by a minimum-cost assignment of the distance from each pad to the nearest pad of its net elsewhere (Kuhn 1955, the Hungarian method). A minimum Euclidean bipartite matching has no crossing pairs, so the group's own ratsnest untangles. The swapped board permutes the pads' own (net ...) nodes; everything else is byte-identical.

    57. --si-rules closes the audit loop: return stitching of critical nets (doc 18 B3, 2026-10-27, D144)¶

    The reference-return audit (§42) and the return-path stitching pass (§39.3) were two commands; --si-rules routed the critical nets with their three rules (§44) and reported void crossings without places. Now, with --si-rules:

    1. After routing, the audit runs on the critical nets. Each layer change it finds with no closure and the same reference net on both sides makes that net a return-path stitching target of that reference net at 5 mm, the audit's own radius (the catalogue's 5.08 mm would leave a stitch the audit does not count).
    2. The stitching pass runs with those targets added to any from --stitch-vias return and the component rules, as a transaction: its vias are kept only if no net has more unconnected items with them after a refill.
    3. The audit runs again. The critical-net report (log, --json critical_nets, the run report) carries missing_stitches per net and in the totals, missing_stitches_before_stitching, and a warning per place: each unstitched layer change with its layers, its position in millimetres and why (no via of the plane net within 5 mm; two different reference nets and no capacitor between them; no reference copper on one side), and each void whose return detour is over 2 mm, with its layer and position. At most eight places per net are listed, then a count.

    --no-si-stitch turns step 2 off. A change between two different reference nets needs a capacitor between them, which is a placement decision: it stays a warning. A layer with no plane copper near the via cannot be fixed with a via either.

    The audit at a layer change also changed: a signal layer whose trace is only a stub from a pad to its via can lie wholly over the via's own antipad, which left that layer with no reference by coverage and reported "no reference copper on one side" between two solid planes. At the via, such a layer now takes the adjacent layer (N+1, then N-1) that has copper within 2 mm of it.

    Test [pour][route][critical] ("route --si-rules stitches the critical nets' layer changes the audit finds without a return via"): a four-layer board, CLK from an F.Cu pad to a B.Cu pad between GND planes on In1.Cu and In2.Cu, the nearest GND pin 10 mm away: one unstitched change before the pass, a GND via beside it after, none in the audit; with --no-si-stitch the warning names the place.

    On the plane tier (bench/records/m21-b3) the critical nets' layer changes are nearly all closed already by the GND pads and stitching the boards carry: one change on StickHub stays open, and it has no plane copper on one side. The pass matters on boards whose critical nets change layers far from any plane via.

    58. KiCad 10 tuning profiles: per-layer width (doc 18 B1, 2026-10-28, D145)¶

    KiCad 10 lets a project define tuning profiles (Board Setup → Tuning Profiles), stored in the .kicad_pro as tuning_profiles.tuning_profiles_impedance_geometric. Each profile has a name, a type (single-ended or differential) and, for each signal layer, a track width and pair gap in nanometres, its reference layers and a propagation delay, plus via delays. A net class names its profile in its tuning_profile field. The engine read none of it.

    Reading. read_design_rules reads the profiles (model::TuningProfile) and each class's tuning_profile, Default's included.

    KiCad's rule. KiCad's DRC engine (pcbnew/drc/drc_engine.cpp) compiles each class's profile into implicit rules. They come before the custom rules, so a .kicad_dru rule overrides them. On each layer with a width, the class's tracks have exactly that width: track_width with min = the larger of the width and the board minimum, and opt = max = the width, under the condition A.hasExactNetclass('C') && A.Layer == 'L'. A differential profile constrains only the pair nets (&& A.inDiffPair('*')) and fixes their gap the same way. When that gap is below the class clearance, it adds a clearance at the gap for AB.isCoupledDiffPair(). The rules carry the severity of tuning_profile_track_geometries, which is ignore unless the project sets it. read_design_rules adds the width and gap rules in the same place (CustomRule::implicit) with that severity, so the engine's DRC judges a board as KiCad does.

    What KiCad 10.0.6 does, measured with kicad-cli (rule_parity cases tuning_profile_* and static_exact_class_*, and the boards in bench/records/m21-b1), differs from the source in three places, and the engine follows the measurement:

    • An ignored rule still decides. At ignore, a profiled track below the board minimum is not reported either: the profile's rule is the one that decides the track's width check, and it is ignored. The DRC now takes track_width's severity from the last matching rule (RuleEngine::track_width_severity).
    • hasExactNetclass matches only in KiCad's own rules. In a user's rule it never matched, whether alone, under && or in a track_width rule, while the profile's rules with the same text did. The engine evaluates it only in implicit rules (renamed internally when compiled). In a user's rule it stays one of the functions taken as false (the table in §27).
    • The coupled clearance covers tracks only. On RoyalBlue with a 0.15 mm profile gap under a 0.2032 mm class clearance, KiCad passed the coupled tracks at 0.15 mm but reported a half's track 0.19 mm from the other half's connector pad. With the same gap set on the net class instead, the pad passes. The engine's reader does not add the coupled rule (it does not evaluate isCoupledDiffPair). The route job sets NetClass::tuning_pair_gap, which relaxes only the halves' tracks against each other (RuleEngine::clearance, route::pair_rule). Pads and the pair's vias keep the class clearance, or the class's own pair gap.

    Routing. The router has one width per net (doc 15 §15). A profiled class is routed as follows:

    • Single-ended. At the widest width the profile gives on the board's layers, so every clearance holds at any of the widths. After routing, each track of the class's nets is narrowed to the profile's width on its layer, in run_route_job. Narrower copper cannot break a clearance, and a track keeps its ends. The step is judged like the other after-route passes: it is dropped if a net has more unconnected items with it.
    • Differential. A pair's gap changes with its width when the centrelines stay put, so narrowing would leave the inner layers at the wrong gap. The pairs are routed at one layer's width and gap: a layer the class's SMD pads are on (a pair kept off its pads' layer could not leave them), then the geometry most of the profile's layers share, then the first. A disallow track rule for the class's pair nets keeps them off every layer with another width or gap. Their uncoupled pieces take the same width, and the tracks of the two halves may sit at the profile's gap (above).

    The profile is applied whatever the severity of KiCad's check: it states the impedance the designer wants, and the check is only whether KiCad reports a miss.

    The log names each profile and its route width. --json has tuning_profiles: the class, the profile, the route width and its layer, each layer's width and gap, the layers kept clear, and the tracks narrowed. A class naming a profile the project does not define is warned about (KiCad's missing_tuning_profile) and routed with its class width.

    Not used yet. The delays (per layer and per via) and time-domain tuning: they belong to B2's length and skew matching. The profile's reference layers are not used: the audit (§42) finds the reference copper itself.

    59. Time-domain matching: delays as KiCad 10.0.6 measures them (doc 18 B2, 2026-10-28, D147)¶

    KiCad 10 measures a net's length and propagation delay in LENGTH_DELAY_CALCULATION (pcbnew/length_delay_calculation). A length or skew constraint given in ps or fs is compared with the delay. The engine read the units but measured lengths its own way, ignored time rules, and had no tuner aiming at a delay.

    Measurement (drc/length.hpp, drc::net_length). This is a port of 10.0.6's calculation, with its quirks:

    • Pieces. A net's tracks and arcs, in file order, are chained where ends meet. In 10.0.6 a chain grows at an end only where exactly one other line end remains, on the same layer, and the first line of each chain is taken out of the search first. On a branched net the result therefore depends on the order KiCad visits the lines, which is the order of their addresses (a std::set of pointers). KiCad master merges only at simple two-end joints.
    • Vias. A via counts when its span is used: a line ends at its centre or strictly inside its disc, or a pad it touches is on the net (an SMD pad on its copper layer, a through-hole pad on its footprint's side). Its height is the stackup distance between the outermost layers used (doc 05 §38's via_heights, moved to drc). A via joining one layer only is a stub: counted, with no height. Without "use height for length calculations", vias count for nothing.
    • Clipping. A chain end inside a via's disc is replaced by a straight line from the via's centre to where the chain crosses the disc's edge. A chain end exactly on a pad's position is clipped at the pad's outline.
    • Rounding. Segment lengths are rounded to the nanometre and arc lengths are truncated. A layer's delay is its delay per mm times the length in mm, truncated to the attosecond. A via's delay is the profile's override for its signal and via layers (upper layer first), else its delay per mm times its height, and only with time-domain tuning on. A pad's die delay counts only when the net has a profile.

    Check (drc.cpp, check_lengths). This is KiCad's matched-length test:

    • Every pad, track, arc and via is grouped by the last rule giving it a length or skew constraint at its layer, then by net. Each group is sorted by net name.
    • A length outside the window is reported on its minimum first. A rule in ps compares the delay.
    • Skew is measured against the net with the most length or delay. In 10.0.6 that net is measured against itself too, so a minimum skew always fails on it (KiCad's QA board shows exactly that one violation). within_diff_pairs pairs each net with its partner.
    • A rule at severity ignore is skipped.

    Net classes, as 10.0.6 resolves them (DesignRules::classes_of). A net's effective class is built from every class that matches it. Default joins when the matched classes leave any of ten fields unset (clearance, track width, via and microvia sizes, pair width and gap, wire and bus width), or when none of them has a tuning profile and Default has one. Such a composite is named "A,Default", so hasExactNetclass('A') misses it. hasNetclass('A') is true when any constituent is named exactly A; it is now evaluated, and was taken as false before. A class with an empty profile takes Default's. Net settings older than schema 5 lose every profile when KiCad migrates them, and the reader does the same and warns. A missing schema version means no migration.

    Coupling check (drc/coupling.hpp, check_diff_pairs). This is a port of KiCad's diff-pair coupling test, which the engine did not have, so diff_pair_gap rules were not checked at all:

    • A P track and an N track on one layer are coupled where their lines are exactly parallel (a zero integer cross product) and not collinear, and their projections overlap. The pair is skipped when anything else on the layer crosses the line between their nearest points, apart from tracks and vias touching the coupled ends and pads that either track leaves.
    • The gap is the centreline distance minus the half widths, with KiCad's rounding. It must lie within the rule, with the DRC epsilon.
    • Items are grouped by pair and rule names under KiCad's key comparator. Its quirk keys an item twice when both a gap and an uncoupled rule apply, so the gap errors are reported even then. diff_pair_uncoupled compares the longer half's track length minus the coupled length.
    • Arc pairs are not coupled (the router writes no arcs).

    A tuning profile's pair gap is a rule with min = max = gap and no uncoupled limit. Every parallel stretch of the two halves that can see the other must therefore be at exactly the gap, which includes stretches far apart with nothing between them.

    Routing (Router::tune_delays, after tune_lengths and tune_skew). Each net with a length rule in ps is tuned into its window. A meander raises the delay by the delay per mm of the layer it is on, so only tracks on layers with a delay are candidates. The tuner measures with the same calculation as the check, and its last meander is cut to fit. Then each skew rule in ps: the nets it groups, or each pair with within_diff_pairs, are brought to within a quarter of the limit below the net with the most delay. Nets of a profiled class are not necked down (§58). When the meanders do not fit, the tuner rips the routed connections in their way and routes them again (§61, D152).

    Pair names (drc::match_dp_suffix, D149). Nets are paired as KiCad 10.0.6's MatchDpSuffix pairs them: - From the end of the name, digits and underscores are skipped. The next character must be P or + (positive) or N or − (negative). - The partner's name swaps that character, so LVDS_N0_1 pairs with LVDS_P0_1. - inDiffPair('x') matches the base, which is the name before that character. If the base ends in an underscore, it also matches the base without it. So D_P1 is in inDiffPair('D') and in inDiffPair('D_').

    Before, the engine looked only at the last character and matched the whole name minus that character, or the whole name. Among the 4,143 fixture boards, only vme-wren (its DDR4 DQS_P0..3/DQS_N0..3) and one freerouting fixture pair differently. Pair routing, the relaxed gap between pair halves and the DRC's pair polarity all use the same pairing.

    Routing around coupling errors (Obstacles::coupling_state, D148). This applies when a pair net has a diff_pair_gap rule, not ignored, with a minimum or a maximum on a layer. A new track of that net is then tested against each track of its partner on that layer with the same coupling test as the check, the same epsilon included. A coupling out of range blocks the track if the partner track is fixed copper. If the partner track was routed, it can be ripped up. The test is part of segment_state, so the exact check at commit applies it to merged segments. The search also applies it to each lattice step of such a net, because otherwise a path that the exact check rejects at the end is found again and again. When looking for something between the two tracks, the router does not consider pad holes on layers that have none of the pad's copper. It is therefore stricter than KiCad there, never looser. Boards without such a rule do not run the test.

    60. Vias and pads that remove unconnected copper (2026-10-28, D150)¶

    KiCad lets a via or a through-hole pad drop its copper on the layers where nothing connects to it (the padstack's "remove unconnected layers"). The engine read such a via as copper on every layer of its span. On boards that use the option it reported clearance and shorting errors against copper KiCad does not have, filled zones around rings that are not there, and on vme-wren judged diff pairs as hidden from each other by rings KiCad had removed.

    Reading (io/kicad/board_reader.cpp). The mode is set token by token in file order, as KiCad's parser sets it: a via's (remove_unused_layers) switches removal on, its (keep_end_layers) keeps the outer layers, its (start_end_only) keeps only them; a pad's (remove_unused_layers) and (keep_end_layers) set the mode either way. (zone_layer_connections ...) lists the layers a zone joins it on.

    Flashing (drc/copper.cpp, drc::flash_layers). A layer of a via or pad that may lose its copper keeps it when the file says a zone joins it there, or when a same-net track, arc, via or pad reaches it on that layer. As in KiCad's connectivity (CN_VISITOR), the item is looked at as its hole on such layers: a track that touches the ring but not the hole does not keep the ring. A pad reaches F.Cu to B.Cu if it is plated through and only its first layer otherwise; the items of the pad's own footprint, and two pads whose layers are both conditional, do not count.

    Copper model. A via or pad with bare layers is two items: its copper on the flashed layers, and a hole-shaped bare part on the others, which KiCad's clearance test checks at copper clearance. The bare part has no connectivity of its own (its root and net are the main item's) and is left out of the checks that look at copper (rings, widths, edges, keepouts, lengths, pairs, dangling); a rule's existsOnLayer and area tests use the whole span.

    Zones (drc/refill.cpp). Before filling, KiCad's filler works out again which layers a zone joins each via and pad on (the highest-priority zone of the net that contains the hole there, with its accuracy and keepout quirks); the refill does the same on a copy of the board. A same-net via that no zone joins on a layer is knocked out of the fill there like another net's.

    Router (route/obstacles.cpp). A new track or via of the net does not flash a bare layer it did not plan to reach, so the router keeps its own net clear of bare parts (and new vias clear of same-net rings that may be removed). This is stricter than KiCad, which would flash the layer and connect them.

    Nearly parallel pairs. KiCad couples two tracks whose lines do not meet (!SEG::Intersect(..., lines)). In line mode SEG reports no crossing when the crossing point does not fit in 32 bits, so tracks a few nanometres off parallel are coupled (vme-wren's DQS0 has two 45° stubs 10 nm off). drc::couple computes the crossing as SEG does and couples them too; the router uses the same function.

    Tuning patterns. KiCad's diff-pair coupling test (isInTuningPattern) leaves out tracks and arcs that are members of a tuning pattern (a (generated (type tuning_pattern) (members ...)) group): they are neither coupled nor counted in the uncoupled length. The reader marks them, and the DRC and the router's coupling test skip them. vme-wren's DDR4 pairs have 89 tuning patterns.

    Results. Four fixture boards use the option: vme-wren and jetson (KiCad demos) and two srj24 samples. None is in a bench tier.

    On vme-wren (bench/records/d150-padstacks) the engine's DRC went from 22,362 clearance and 21 shorting reports, where KiCad reports none, to 425 and 20. Those left have other causes: pad-to-track pairs judged at 0.125 mm where KiCad resolves 0.1 mm, and shorts against copper graphics. With flashing, tuning patterns and nearly parallel pairs, its 28 coupling-gap errors and 6 uncoupled-length errors are KiCad's, values included. jetson still matches KiCad on the routing-relevant types. The eight B1/B2 boards with pair rules route byte for byte as before.

    • [flash], two cases: modes read in file order and the layers flashed for a via with an inner track, a zone connection, no end layers, start-end only and none; the refill joining a GND via to its plane and filling up to a bare S hole, with no DRC errors.
    • [coupling], two cases: tracks in a tuning pattern are not coupled, members of a plain group are; DQS0's stubs 10 nm off parallel are coupled at KiCad's 1.8573 mm.
    • rule_parity: via_unused_layers (four vias, each passed by tracks inside the ring's clearance and outside the hole's) and diff_pair_tuning_pattern and diff_pair_near_parallel. All 234 cases match; the build before D150 fails these three.

    61. Delay tuning that makes room (2026-10-28, D152)¶

    The delay tuner (§59) puts a meander only where nothing else is. When it runs, after negotiation and clean-up, the board's other connections are all in place. On RoyalBlue54L-Feather-delay with D139, the extra connections took the room beside the USB pair. D+ stayed 2.7 ps short of D- against a 0.5 ps rule, and KiCad reported skew_out_of_range.

    Router::tune_with_room. It applies to every delay window and every delay skew group or pair.

    1. Plain tuning first. If the net ends in range, the step stops there.
    2. Start over from the untuned net. The board goes back to the net with no meanders, because the small meanders of the plain attempt fill the free room.
    3. Try ripping at each height. After both free sides of a meander, the tuner tries each side that only routed copper of other nets blocks. The rippable owners are those segment_state reports when routed copper is ignored. Those connections are ripped and the meander is placed.
    4. Who may be ripped. A connection may be ripped if it is:
    5. routed, and not implicit;
    6. not coupled, and not a bus or bundle lane;
    7. not of the net or of its pair partner;
    8. of a net with no length or skew rule of its own.

    At most 16 connections are ripped. 5. Route them again. The ripped connections, and those of their nets that lose an implicit route, are routed again strictly, in connection order. Each gets the transaction cap. Together they get 400,000 work units beyond the spent budget (2 % of the time limit with --time). 6. Keep or roll back. The board is kept if the net is in range and all of them route again. Otherwise it goes back to the plain attempt's result.

    Result (bench/records/d152-room, 3 M work, --refill --soft-zones). RoyalBlue54L-Feather-delay routes 125/147 with no added KiCad errors. One connection is ripped and routed again, and D+ ends at 79.43 ps against D-'s 79.49 ps. The other B2 boards never reach the step. Test: delay_room (it skips without build/demos).

    Open. mm length windows, mm pair skew and the bus tuner do not make room yet.

    62. Search speed: late reachability proofs and output-preserving speed-ups (2026-10-29, D154)¶

    Where the time went. gprof on five hard PCBench boards (logicbone, sbc, Teensy_test_layout, LeeChee, kitspace_d20), one variant, 20 M work, CPU fields: the A* loop 27–57 % of CPU, cost-to-go fields on the CPU 14–33 %, legality checks most of the rest. Every board spent the whole budget in the strict first pass. A few failed searches took most of it: 15 failures 77 % of logicbone's budget, 108 failures 84 % of sbc's, 60 failures 91 % of kitspace_d20's. Successful searches expanded a median of 30–230 states. A per-search log showed that most failures exhaust their region (no path exists) rather than hit the 3 M cap. On LeeChee 28 % of the run was point_in_polygon on its 572-edge outline, called by the inside-board test in boundary cells. Records in bench/records/d154-speed.

    What changed.

    Change Output Effect
    Late reachability proof (--reach-after 100000, --reach-after-cap 10000) changes (exact; more budget left for the rest) see below
    CPU field: the six sweeps that change row, and the via step, run a row at a time without branches and vectorise (field_cpu.cpp gets -ftree-vectorize -fvect-cost-model=dynamic under GCC); the line-by-line version is field_cpu_reference identical (fields and round counts; test) field time about halved (logicbone 9.5 → 5.3 s at 20 M)
    Inside-board test: the outline's and cut-outs' edges indexed by raster row; a point in a boundary cell is tested against its row's edges only (Obstacles::inside_exact, reference inside_exact_linear) identical (test on a toothed outline with a round cut-out, points on edges and row boundaries) LeeChee 27.6 → 18.2 s CPU; a --global run there 158 → 7.5 s (§19)
    Per-class obstacle caches (LazyCodes) allocated in chunks of 4,096 codes on first write; unwritten chunks read as not computed identical memory per router 1.6 GB → 0.56 GB (Teensy), 1.65 GB → 0.44 GB (logicbone)
    Target marks of a search in a reused buffer instead of a fresh array per search identical small

    Late reachability proof. The pre-check of §13 floods before a strict search; run on every search (--reach-check 2) it pays a flood on searches that would have succeeded at once. The late proof instead runs only inside a strict search that has expanded reach_after states without reaching its target. Two floods, forward from the sources and backward from the targets, take a cell in turn, over the pre-check's moves (no bends, turn limits or costs; any via landing the A* allows, including on target cells of layers without tracks). The backward flood enters a cell's neighbours when a planar move may enter the cell (it is a target or legal), and the cell's other layers when a via may land on it. Both admit every path the A* can find, so when one runs out before they meet there is no path. The search stops as an enclosure (the region did not touch the window edge; when it is the target's, "boxed in (target)", which spares the reverse probe) or a window miss. When they meet, or reach_after_cap cells are visited, the A* goes on as before: the floods only filled the legality caches it reads. Flood cells count against --work at --flood-work-pct, as the pre-check's do. --reach-verify runs the A* on after every proof and counts paths it finds: 0 on the five boards (the proof at 20,000 expansions, no cap: 389 proofs, 64 of them "no path"). Breakout boards keep the pre-check on every strict search (D98), so the late proof does not run there.

    63. Finishing the last connections: end-game retry, pin rescue, plane fallback (2026-10-29, D155)¶

    Items 1, 2 and part of 4 of the M22 plan (doc 18 §18). All of it is off by default, and with it off the output is byte-identical to 0.12.1 (the 30 quick boards at 1 M work, every routed .kicad_pcb compared). Records in bench/records/m22-endgame.

    What was built.

    • End-game retry (--endgame F, --endgame-cap N): when the main loop ends with connections open, the board is put back to its best state (only the connections whose copper differs are lifted) and the router gets F of the budget more. Each open connection that is not proved dead goes once more, shortest first, as a plain search capped at N expansions, then a pin rescue if it is boxed in, then the plane fallback. The result is kept only from the best state, so the clean-up stages still run.
    • Pin rescue (--rescue 2,4,8, --rescue-orders, --rescue-victims, --rescue-cap, --rescue-per-conn, --rescue-in-loop): for a connection proved boxed in, the routed connections with copper within r of either end are lifted (none that are coupled, bus lanes, bundle lanes, first nets or bus nets for a plain net; a radius that would lift more than --rescue-victims ends it). The boxed connection is routed first. Each lifted connection whose old copper still passes the exact check gets it back unchanged; the others are routed again in seeded orders. It is kept only when all of them route; else everything is put back exactly. On failure the radius widens: this is the user's "widen and randomise the last traces", applied to what is ripped, not to the search's costs. By default it runs only inside the end-game; --rescue-in-loop also runs it in the main loop.
    • Informed pad-to-plane searches (--plane-informed, --plane-fallback-mm): the A* to a zone uses the octile distance to the zone's box as its bound and may run the late reachability proof (§62) forward to the zone. When the search fails, the connection is planned from a nearby pad already joined to the plane, from another pad of the same group, or to another fill of the net.

    64. The last connections, developed on one board: via shove, fan-out hold, negotiation bounds (2026-10-30, D156)¶

    M22 developed on one board, as the user asked: mini_mass_prog_bench_prog_rig (995 connections, 986 routed in every earlier arm). Each change was tried there alone, and the other failing boards were run only at the end. Everything is off by default, and with it off the output is byte-identical (the 30 quick boards). Records in bench/records/m22-oneboard.

    What the board showed.

    • The nine open connections are all on U2, a 0.5 mm QFN-44. Six are pins boxed in by their neighbours' fan-out within 0.25-1.25 mm. Three are INT nets about 450 mm long, boxed in at U2 in the first pass.
    • More budget does not move it: 40 M and 60 M route 986. The first pass is the same at every budget. In negotiation, each open connection first retries strictly, which fails (25 M of 30 M at 40 M work). Its negotiated search then finds a path in 18 k-1.4 M expansions.
    • Every negotiated success rips other long nets, which go back into the same pass, so the pass never ends. Bounded, the passes route 986, 970, 966, 961, 958, 971, 969, 974: negotiation on this board loses.

    What was built.

    • Via shove (--via-shove, --via-shove-mm, --via-shove-step, --via-shove-rings, --via-shove-trials, --via-shove-share). KiCad's push-and-shove via move, as a repair step of the batch router: a boxed-in connection moves other nets' vias nearby, and only the tracks ending at them.
    • The nearest vias are lifted one at a time, then in pairs, and the connection is searched once without them (strict, capped).
    • If it routes, each via goes down at the nearest position on 6 rings of 16 where it and its re-drawn legs pass the exact check.
    • If no position fits beside the new route, the via is put at each position in turn and the connection searched round it.
    • Otherwise everything is put back.
    • It spends at most 5 % of the run's work budget. Unbounded, it routed 10 connections on kitspace_d20 and lost 41 through the budget it took from the main loop.
    • Fan-out hold (--fanout-hold): each open pin's straight escape corridor is held by a placeholder track of its net through the strict pass. It is dropped when the pin is routed or the pass ends.
    • Negotiation bounds (--neg-strict-cap, --long-weight, --long-weight-mm, --pass-bound): a cap on negotiation's strict searches, weighted A* (Pohl 1970) for long negotiated searches, and passes limited to what was queued at their start (PathFinder's iterations).
    • Items 3, 5 and 6 of the plan: --window-escalate (one whole-board window after an edge miss), --via-retry (D153, after a cap miss only), --escape-all (the escape plan in every variant) and --pin-via-pen (a via in another net's dense-pin fan-out region costs more).

    Results. On mini_mass the via shove routes 987: I2C_SCL, open in every earlier run, after an I2C_SDA via moves 0.45 mm. The fan-out hold moves the failures between U2 pins (979-987). The negotiation bounds and items 3 and 5 leave it at 986.

    65. Fan-out heads: the designer's escapes laid before routing (2026-10-30, D157)¶

    M22 item 8, developed on mini_mass_prog_bench_prog_rig like §64. Its open pins are on U2, a 0.5 mm QFN-44. Their neighbours' escapes and a ring of vias 1-2 mm out box them in.

    The oracle. The designer's copper near U2 was put into the unrouted board as fixed copper (variant 6, 20 M work):

    Copper put in Routed
    none (base) 986 / 995
    all within 5 mm 969 / 973 (it completes 22 local connections itself)
    only the parts touching one pad (escape heads) 990 / 995
    only the parts joining two or more pads 967 / 973
    straight 5 mm stubs from every pin 978 / 989
    the same, no GND/+5V pins 983 / 993

    The escape heads alone are worth four connections, and straight stubs do worse than nothing. The designer keeps each side straight, or bends its pins in staggered 45-degree bundles toward their destinations. A side stays straight where its bundles would run into the parts beside the package: on U2 the top pins' destinations are more sideways than the left pins', yet the top runs straight. Angle rules alone failed: always bending gave 983-984, bending past 60 degrees 986-987.

    The heads (--fanout-heads MM, route/fanout_heads.hpp). Before the obstacles are built, each perimeter pin of a package with pins on all four sides (24 or more) gets a head on its pad's layer, MM past the package.

    • Along a side the pins split into a block that turns toward the low end, a straight block and a block that turns toward the high end. This is ordered escape with one bend (Kong, Yan and Wong, ASP-DAC 2010). A pin turns when its destination is more than 30 degrees off the side's normal.
    • Turning pins bend from 0.3 mm past the pad, each 0.1 mm further out than its neighbour toward the corner, so parallel diagonals keep track plus clearance apart.
    • Each side is laid both ways and keeps the way with more head length.
    • Each leg stops where the exact check refuses it, and a cut head ends 0.5 mm short of the obstacle.
    • No head for:
    • nets with a zone;
    • pins whose nearest off-package pad of the net is within MM (local connections);
    • copper that would come near other copper of the net (so a head joins nothing).

    The heads are fixed copper of their net while the board is routed: other nets go round them, and the pin's own route runs over its head. They are not routed copper, so they are not written out. Each route runs pad to pad, so leaving them out disconnects nothing.

    Results on mini_mass. --fanout-heads 5 routes 989 of 995 and --fanout-heads 3 988; the base routes 986. Adding --via-shove keeps 989. The KiCad DRC of the output adds nothing. Still open:

    • RESET (U2.13);
    • USB_D- (U2.3);
    • +5V C1-R6;
    • the three INT nets (about 450 mm), which fail on the search budget, not on escape.

    On the ten failing boards (8 variants, 20 M work) --fanout-heads 5 routes 7,175, the same as the base. The base at 22 M routes 7,193 and --via-shove --escape-all 7,197. Of the six boards that get heads, two gain 3, one is unchanged, and three lose 1-3. Adding --via-shove --escape-all gives 7,190.

    Status. Off by default; with it off the output is byte-identical. What a side of a package should do is decided here from free head length alone. That fits U2 on mini_mass and not the packages of CoreOne, EtherCAT and poncho.

    CoreOne oracle. The same oracle on CoreOne's U801 (a 0.4 mm QFP-128) routes 785 of 806 with the designer's single-pad copper, against 787 of 807 for the base; our heads on U801 alone route 786. There, 51 of the designer's 70 heads end at a via within 3 mm, so the escapes are fan-out vias rather than F.Cu runs, and even they do not help. No better rule for the heads could win on that board, so the work stopped. A single variant moves by up to 10 connections between arms with the same best-of result, so the -1 to -3 per board above is within that spread (records: bench/records/m22-oneboard/heads/coreone).
