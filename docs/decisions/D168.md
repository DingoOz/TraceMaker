# D168 — The router keeps custom hole_to_hole and edge_clearance rules at one board-wide value

## Context

Issue #52: the router read only the board minimums for hole to hole and copper to edge (`Obstacles::holes_edges_state`, `fixed_code`,
`fixed_via_code`, `via_hole_code`), so custom `hole_to_hole` and `edge_clearance` rules were ignored while routing and KiCad's DRC then
flagged the result. WholeBoard asks for 0.5 mm hole to hole between nets (`A.Net != B.Net`), and TraceMaker did not evaluate `Net` at
all: the rule was dropped by the DRC too. Doc 05 §27; records in `bench/records/issue52/`.

## Decision

- `Net` is evaluated as KiCad does: the net code, a number (`PROPERTY_ENUM<BOARD_CONNECTED_ITEM, int>`). Five rule-parity cases judged by
  KiCad 10.0.6 fix the semantics, including the single unitless literal (`A.Net == 2`) that drops the condition.
- `RuleEngine::router_hole_to_hole()` is the board minimum raised to every applied `hole_to_hole` rule (valid, not severity ignore). The
  router keeps it between a new via's hole and every other hole: the exact check, cached via codes, routed vias, diff-pair via offsets
  and the legaliser (`LegalizeOptions::hole_to_hole`). A rule with a condition or a layer is kept everywhere and warned by name, as D140
  does for `hole_clearance`.
- `RuleEngine::router_edge_clearance()` is the board minimum raised to every applied `edge_clearance` rule that can hold for a new track or
  via: the condition is asked for a track and a via of each net on each layer, and a positional condition is assumed to hold. A rule that
  selects only zones or pads leaves the router alone. One that misses some tracks or vias, or has a layer, is warned by name. Non-plated
  holes, which KiCad treats as edges, take the same value.
- The DRC is unchanged: it already evaluated both rules per item and pair, and now reads `Net`.
- Neither value depends on the probe's net, so the per-class caches stay valid; these rules never ask for the exact path.

## Alternatives

- Per pair in the router (the exact `RuleEngine::hole_to_hole` for each nearby hole, a per-net edge table). The exact check could afford
  it, but the cached via codes judge a class with one stand-in net, so `A.Net != B.Net` or a `NetName` condition would need the exact
  path board-wide (D139), several times slower on boards with JLCPCB's rules. The conservative value costs little: hole to hole and edge
  values are a few tenths of a millimetre, and only vias near holes or copper near the outline are affected.
- The same "can it hold for a track or via" test for `hole_to_hole`. A pair condition (`A.NetClass == 'X' && B.NetClass == 'Y'`) needs
  every pair of nets, and a test over fewer pairs could miss one; the rule is kept everywhere instead.

## Consequences

- relaymini with `A.Net != B.Net` hole to hole at 1 mm and an 0.8 mm `edge_clearance` for tracks and vias (3 M work, 2 variants): KiCad
  reports 9 `hole_to_hole` and 6 rule `copper_edge_clearance` violations before, 0 and 0 after; 60/72 routed before, 59/72 after (the
  conservative value also spaces a net's own vias, and the router places 35 vias instead of 44).
- A conditional `hole_to_hole` rule also keeps a net's own vias apart, which KiCad would allow when the condition excludes them.
- A literal net code (`A.Net == 5`) is compared with TraceMaker's numbering, nets in file order; KiCad 10 files name nets without codes, so
  such a rule may select another net than in KiCad. Comparing two items' nets is exact.
- Doc 05 §27 and §33, doc 08, the board-prep skill's rule table and preflight (these rules keep the caches).
