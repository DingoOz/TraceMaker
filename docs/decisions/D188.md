# D188 — Return-path audit of critical nets in every run report

## Context

M23 E4 (doc 18 §20). The return-path audit (doc 05 §42) and the critical-net report (§44) ran only when asked for. A default run, and so
the plugin's run report, said nothing about whether fast nets keep their reference copper (user point 7).

## Decision

- On a board with a zone of a net and more than one copper layer, and with no critical-net option given, the nets `--critical-auto` would
  find are found and audited after the route. It is a report only: they are not passed to the router. `--no-critical-audit` turns it off.
- The summary's `critical_nets` gets `"mode": "audit"`. The run report says how the nets were found, warns only on a return-path fault (a
  split, a layer change with no return within reach, a detour over the 2 mm threshold), and says so when no such net exists.
- Doc 05 §81.

## Alternatives

- **Turning on `--critical-auto` itself by default**: it may reorder and reprice routing, which changes completion; the audit alone cannot.
- **Name patterns (`*CLK*`, `*USB*`)**: the component roles and pairs already find these nets with fewer false hits. A user's patterns stay
  available through `--critical-nets` and `--return-paths`.
- **Flagging open connections too**: the Result section has them, and flagging them would mark every unfinished board.

## Consequences

Every planes-set board's report has the section: StickHub and interf_u are flagged, RoyalBlue54L-Feather and plane_smd are clean, and 4
boards have no critical net. The copper is byte-identical with and without it, at no measurable time. Records: `bench/records/m23-e4`.
