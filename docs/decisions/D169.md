# D169 — Obstacle caches are keyed by class values and bounded in memory

## Context

Issue #54: the router keeps one fixed-obstacle cache (track codes with and without the lattice margin, via codes) per net class and
track width, per variant. A board with 83 net classes (WholeBoard wrote one class per impedance pair) reached 181 GB of the machine's
184 GB after 17 minutes with 8 variants, once D139 turned the cache on for its rules. D154 already allocates the caches in chunks as
cells are reached (`LazyCodes`), but nothing bounded the total, and classes with the same values each computed the same codes again.
Doc 05 §72; records in `bench/records/issue54/`.

## Decision

- A cache is keyed by what its codes depend on (`CacheKey` in `route/router.cpp`): the class's clearance, diff-pair gap and tuning-pair
  gap (the values `RuleEngine::clearance` reads for the probe net), the track width, and the via diameter and drill. Classes with the same
  values share a cache, as the nets of one class already did.
- When a custom rule's condition reads class names (`NetClass`, `hasNetclass`, `hasExactNetclass`; `RuleEngine::class_names_seen`), two
  classes with the same values may be judged differently, so the key also holds the class and the caches stay per class.
- The via size in the key replaces the "neck-down via" bit. A net that may not neck down (`--no-neck`) keeps the class via on the
  neck-down rung, and used to share via codes that another net of the class may have computed for the smaller via.
- `--class-cache-mb` (default 2048, 0 = none) bounds each router's caches. Past it, the caches used longest ago (not the one being
  switched to) are freed. A freed cache keeps its probe net, so a code asked again comes back the same. The cost-to-go fields use only
  the codes known so far, though (`build_field`), so a run that reaches the bound can route differently from one that does not; the
  order of switches, and so the result, stays deterministic and independent of the thread count. Each cache holds at most a whole
  lattice, so the total stays below the bound plus one cache. The route log prints a `note:` with the number of evictions when the
  bound was reached. The default is far above what the boards measured so far need (D154: 0.44-0.56 GB per router in all).

## Alternatives

- Size the arrays to the routed windows: the caches already grow only where searches go (D154); a cache per window would be thrown away
  and rebuilt for each connection.
- Merge equal classes in the reader: the DRC, the reports and class-name rules need the classes as the project names them.
- A bound per cache: a board with many distinct classes would still multiply it.
- A bound that keeps the result: freed codes would have to stay known to the fields, which is most of their memory.

## Consequences

- Boards whose classes all differ get the same caches as before and the same result (unless they have `--no-neck` nets and reach the
  neck-down rung). A board with classes of equal values shares their caches. With coupled pairs, a shared cache judges cells near its
  probe net's partner with the pair gap, as a class holding several pairs already did; the exact check before commit is unchanged.
- `RouteResult::obstacle_caches` and `cache_evictions` report what a run made and freed.
- Measured with every net in a class of its own, the values unchanged (`bench/records/issue54/`): the output is the same as with the
  project's classes, on main and on this change; main makes one cache per class, this change one per set of values.
