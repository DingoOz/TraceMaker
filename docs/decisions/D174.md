# D174 — Per-layer preferred directions by name and a 45-degree penalty

Proposed by quanln (GitHub @quanln) in issue #66; the design (both options, their names and the diagonal penalty) is theirs. Their
patch is in a fork that is not public, so this is our own implementation of it.

## Context

`--layer-dir-pen` and `--layer-dir-swap` (D98) set a layer's preferred direction from its index: even layers horizontal, odd vertical,
or the reverse. quanln's study of 16 hand-routed boards found no single convention (F.Cu mostly horizontal on 6 of 13, vertical on 1,
mixed on 7), and on relaymini the penalty turned orthogonal runs into 45-degree zigzags, since a diagonal step costs nothing against
either direction (45-degree share 31 → 44 % on F.Cu on 0.12.1). They asked for directions by layer name and a penalty for 45-degree
runs. Doc 05 §73; records in `bench/records/issue66/`.

## Decision

- `--layer-dir LAYER=h|v|none,...` gives preferred directions by layer name (`RouterOptions::layer_dir`, per copper index). Given, it
  replaces the parity: layers not named have no preferred direction and `--layer-dir-swap` is ignored with a warning. Its strength is
  `--layer-dir-pen`; left automatic (negative), it is the absolute value (−1: 0.3) on any board, not only on breakout boards.
- `--layer-diag-pen P` (every layer) or `LAYER=P,...` (0 to 100 pitches; named layers override a bare value) adds P pitches to every
  45-degree lattice step on the layer (`RouterOptions::layer_diag_pen`). Independent of the directions.
- Both are integer costs in the search's planar move, next to the parity penalty. The cost-to-go fields leave them out (a lower bound
  stays one), so the CPU and GPU fields are unchanged and need no new test of their agreement.
- Path smoothing keeps the direction costs when the user asked for them (`--layer-dir`, an explicit positive `--layer-dir-pen`, or a
  diagonal penalty on the layer): a shortcut is taken only if its cost under them is not above the run's, and the orthogonal corners
  are candidates too. The automatic strengths of D98 keep the plain smoothing.
- Layer names are checked against the board: an unknown one is a warning and its entry is dropped; a malformed entry, a bad value or a
  duplicate layer stops the run (checked before the board is read).
- Both off by default; with neither given the output is byte-identical.

## Alternatives

- **Hints in the advice file** (doc 17, `layers.direction`). The advice file holds hints for extra, advised variants next to the plain
  ones; a layer convention is meant for every variant and is set by the person running the job, so it belongs with `--layer-cost` on
  the command line (and in `--config` files). Not added; it can be, on the same parser, if an advisor needs it.
- **Unknown layer names as errors**, as `--layer-cost` does. A board-independent options file (a company's convention) may name inner
  layers a two-layer board lacks; a warning names the layer and the board's layers, so the input is not misread silently.
- **Smoothing left as it was.** On the test board it put the diagonal back that the penalty had removed (an L-shaped track became
  diagonal-first again), so the option would mostly not have worked.
- **Diagonal penalty only on layers with a direction.** Coupling the two would make "fewer 45-degree runs" impossible without a direction.

## Consequences

- relaymini, 3 M work, two variants (F.Cu asked vertical, B.Cu horizontal, strength 1.0): runs against the asked direction fall to
  0.6 % / 1.4 %, 45-degree runs rise to 37 / 50 % (the issue's observation); with `--layer-diag-pen 1.0` they fall to 26 / 23 %, below
  the default's 31 / 42 %. Routed 60-64 of 72 throughout. Track length grows up to 25 %.
- Default runs are byte-identical to main (relaymini; srj20 sample001, where D98 is on). `--layer-dir-swap --layer-dir-pen 1.0`
  changes a little (smoothing now keeps the costs), naming the parity's directions gives exactly the parity's output.
- One public board: the effect on completion elsewhere is not measured, which is why both stay off.
- The coupled-pair search does not use the costs; the Python bindings and the KiCad plugin do not expose the options.
