# D170 — Type-only rule conditions are tabled; the pair phase can be given a budget share

## Context

Issue #53: with WholeBoard's JLCPCB clearance rule (`A.Type != 'Zone' && B.Type != 'Zone'`, 0.09 mm, below the 0.15 mm net
classes), six of eight `--diff-pairs` variants on the 10-port PoE switch stopped at about 116 connections after 300 s; without the rule
they reached 880-1000 (`bench/records/d139/`). The issue suspected something sized from the class clearance disagreeing with the rule
engine. Doc 05 §76; records in `bench/records/issue53/`.

What the measurements show instead (`--no-kb`, so every run routes in the same order):

- Every stalled variant was still in the coupled pair phase when the time ran out (`TM_DEBUG_TIMING`, `TM_DEBUG_PAIRS`): about 116 is
  the pairs' own connections. The pair search checks every move exactly (`segment_state`, `via_state` on both halves), so a pair that
  reaches the 250 k-state cap without a legal end takes 10-36 s of wall time. Without the rule the phase is just short enough to finish
  in some variants; on a loaded machine it does not finish without the rule either (106 per stalled variant).
- At a fixed work budget the rule routes the same as an unconditional 0.09 mm rule, byte for byte, but 55 % slower in wall time
  (one variant, 2 M work: 189 s against 122 s). Nothing sized from the class disagrees: the cost is evaluating the condition. The
  exact checks ask `RuleEngine::clearance` for every item near every probe, and each evaluation built, lower-cased and wildcard-matched
  strings for `A.Type` and `B.Type`, twice when the first order did not match (gprof: `str_eq`, `wildcard_match`, string copies and
  `custom_min` among the top entries).

## Decision

- A condition that reads nothing but `A.Type` and `B.Type` is a function of the two items' kinds. `RuleEngine` evaluates it once per
  pair of kinds (6 kinds, B absent included) when it is built, and `custom_min` reads the table instead of evaluating the condition.
  This covers every constraint type `custom_min` serves (clearance, hole clearance, hole to hole, edge clearance, track width). The
  answers are the same by construction; `RuleEngine::use_kind_tables(false)` is the reference path, and the test "kind tables" checks
  that both give the same clearances for every pair of items and probes on a board with pads, tracks, vias and a zone fill. On by
  default.
- `--pair-share X` (`RouterOptions::pair_share`, default 0 = no limit): the coupled pair searches stop once they have spent X of the
  work budget (of the time limit without one), over every call of the pair phase in the run (first pass, restarts, re-coupling); the
  pairs left are routed as single connections and the route log counts the attempts skipped. Checked where the work budget is, so a
  running attempt stops within 64 candidates and the result stays deterministic under `--work`.

## Alternatives

- A per-connection work cap, as the issue suggested: each pair attempt is already capped (40 k-250 k states, doc 05 §15), and an
  ordinary connection's search is capped by `max_expansions`. What took the budget was the phase as a whole (81 pairs), so the limit is a
  share of the budget for the phase.
- `--pair-share 0.25` by default: in the 300 s portfolio it lifted every variant above 1,000 connections (best 1,111 against 1,105),
  but the best variant coupled 19 pairs instead of 75. The run keeps only the best variant, so completion barely moves while coupling,
  the reason for `--diff-pairs`, drops. Left off; a designer who prefers completion can ask for it.
- Memoising every condition by item signature (nets, classes): conditions on nets would need a key per pair of nets and a lock or a
  per-thread table. Type-only conditions are what the manufacturer rule sets write; others stay evaluated each time.
- Faster string comparison inside the evaluator: smaller gain, and every condition still pays per call.

## Consequences

- PoE switch with the rule, eight variants, 300 s, same machine at the same time: work done 44.7 M → 89.7 M expansions; stalled variants
  96 → 126-140 connections (variant 2: 160 → 660); best 1,097 → 1,105 with 75 coupled pairs either way. With `--pair-share 0.25`: every
  variant 1,027-1,111, 19 coupled pairs.
- One variant at 2 M work: the same board file as before; 189 s → 86 s (an unconditional 0.09 mm rule: 84 s).
- Public repro, StickHub (8 USB pairs, 0.15 mm class) with the same rule, `--soft-zones --diff-pairs`, 5 M work: same board file, CPU
  31.8 s → 21.0 s.
- Results do not change anywhere (the tables give the same answers; `--pair-share` is off), so the quick tier was not rerun: none of
  its boards has a custom rule.
- Open: the pair phase is still slow in wall time per unit of work (every move is an exact check, turns and via moves are not
  memoised like straight steps), and conditions on nets are still evaluated per call.
