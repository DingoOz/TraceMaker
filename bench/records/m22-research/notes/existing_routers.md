## Q1. Which tools run an explicit fan-out pass before routing, and how do they place fan-out vias (direction, distance from pad, grid, alternating patterns for BGAs)?

### Takeaway
Nearly every production router has a separate component-level fan-out pass that runs before the main router. The commercial ones (Altium Situs, Specctra/Allegro, Xpedition/PADS, Zuken Dragon EX) choose vias by pattern, using rule-driven templates: direction in/out/alternating, inline vs staggered rows, BGA quadrant diagonals, via close to the pad vs centred between pads. Freerouting's fan-out is not a pattern. It is its ordinary maze search, stopped at the first via, with a distance window (via at least 2.5 mm from the pin centre by default, start-layer expansion within 4.5 mm). Freerouting found that an eager fan-out hurts two-layer BGA boards, and now switches it off or replaces it with direct-first routing in that case. tscircuit has a separate BGA fan-out pipeline (an external `@tscircuit/fanout-solver`) and an escape-via solver for pour-connected nets.

### Cited Findings

**Freerouting: fan-out pass [src]**
- Fan-out is on by default: `settings.fanout.enabled = true`, `maxPasses = 20`, `maxMillisecondsPerPin = 10000`, `ripupAllowed = true`, `minEscapeLengthMm = 2.5`, `maxEscapeLengthMm = 4.5`, `startViaDiameterMm = endViaDiameterMm = 0.250`, `pinSortingOrder = "outer_first"`, `fallbackToBoardVias = true`, `retryWithoutEscapeWindow = false`, `strategy = "eager"` — [FR/settings/sources/DefaultSettings.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/settings/sources/DefaultSettings.java) (lines ~226–240).
- Orchestration in `BatchFanout.fanoutBoard()`: up to `maxPasses` passes. Each pass walks components sorted by SMD pin count, descending, with ties broken by component id; within a component it walks pins in `pinSortingOrder`. The run stops when a pass routes 0 pins, when the board hash is unchanged, or when a 3-pass "oscillation detector" sees the same (routedCount, viaCount). That detector was added after "14 identical passes on a dense SMD carrier" where "pins keep ripping each other's escapes" — [FR/autoroute/pipeline/BatchFanout.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/pipeline/BatchFanout.java).
- Pin orders available (`BatchFanout.Component.Pin.compareTo`): `inner_first` and `outer_first` (distance from the component's SMD-pin centre of gravity), `distanceToClosestOnNet`, and `surroundingsDensity` (count of SMD pins within 20 mm, densest first). Ties are broken by pin index — same file.
- Rip-up cost in fan-out pass n is `startRipupCosts * (n+1)` (default `DEFAULT_START_RIPUP_COSTS = 100`). A negative value means no rip-up — same file, `fanoutPass()`.
- A failed pin is retried only when its component has escaped another pin since that failure (`failedPinGeneration` / `componentGeneration` maps) — same file.
- Single-pin escape is `RoutingBoard.fanout(pin, …)`. It applies only to single-layer pins of one net that are not yet connected off-layer. It builds an `AutorouteControl` with `isFanout = true` and `removeUnconnectedVias = false`. With ≤4 unconnected targets it first routes toward the closest one, then toward the whole set; larger nets route to the whole set at once "to avoid CPU thrashing". It optionally falls back to the board's default via rule (`fanoutFallbackViaRule`) and retries without the escape window if `retryWithoutEscapeWindow` is set — [FR/board/facade/RoutingBoard.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/board/facade/RoutingBoard.java) (lines ~1000–1130).
- How a fan-out via is chosen: the maze search ends as soon as it has passed through one drill ("algorithm completed after the first drill"). So the via lands wherever the cost-ordered expansion reaches a drill first; there is no pattern — [FR/autoroute/maze/MazeSearchEngine.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/maze/MazeSearchEngine.java) (~line 362).
- The fan-out escape window lives in the `mazeExpansionList.add()` override. On the pin's layer, expansions whose entry point is farther than `maxEscapeLengthMm` (code fallback 3.0 mm; default setting 4.5 mm) from the pin centre are dropped. Drills closer than `minEscapeLengthMm` (code fallback 0.5 mm; default setting 2.5 mm) to the pin centre are rejected — same file (~lines 85–122).
- Via candidate sites, for fan-out and normal routing alike (`DrillPage.getDrills`): the board is tiled into drill pages. For each page, every obstacle shape on any layer (other than drillable same-net items) is cut out, the remaining free area is split into convex pieces, and one candidate via (`ExpansionDrill`) goes at each piece's centre of gravity. If SMD attach is allowed, the candidate goes at the pin centre inside the piece, which is how via-in-pad happens. With `centreOfGravityViaCandidate`, a pad-containing piece also offers its centroid. So candidate vias are sparse and gridless — [FR/autoroute/drill/DrillPage.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/drill/DrillPage.java), [FR/autoroute/drill/ExpansionDrill.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/drill/ExpansionDrill.java).
- Via-in-pad and via-touching-pad are separate switches (`AutorouteControl.viaInPad`, `viaTouchingPad`, `viaAttachAllowed`, `viaHoleAllowed`). `fanoutViaPadGap` is "extra cost for fanout vias inside own-net pad clearance" (default 0.0) — [FR/autoroute/maze/AutorouteControl.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/maze/AutorouteControl.java).
- `DirectPinRouting`: "Same-layer pin connections before any escape via. Existing traces and vias stay fixed for the pass, vias and rip-up are off, and a failed pin is left for the autorouter." It is selected by `fanout.strategy = "direct_first"` — [FR/autoroute/pipeline/DirectPinRouting.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/pipeline/DirectPinRouting.java).
- `ExitStubs` (`router.autorouter.exit_stubs`) places "the straight way out of a fine-pitch pin whose only way out meets the clearances to its neighbours exactly … before the fanout as a designer draws it". Stubs are `USER_FIXED`. Constants: `MIN_PINS = 8`, `TIGHT_SLACK = 2*clearance_safety_margin`, `INWARD_REACH_PAD_LENGTHS = 3.0` — [FR/autoroute/pipeline/ExitStubs.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/pipeline/ExitStubs.java).
- `TwoLayerBga`: "On two layers every escape via closes both layers, and the eager fanout drills one beside each ball first. On decelerator4030 (two 0.75 mm BGAs, 0.1 mm traces) its first pass drilled 417 vias and the board stalled at 20 open at the Tier C cap, where without the fanout it ends at 2 and direct-first at 6; the designer escapes the balls row by row on the top layer with almost no vias." On boards with exactly two signal layers and a ball grid, the policy sets the fan-out to `no_fanout` or `direct_first`. Ball-grid detection: at least 16 single-layer pins filling at least half of a grid of 3 or more rows and columns, mostly round pads — [FR/autoroute/pipeline/TwoLayerBga.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/pipeline/TwoLayerBga.java).
- `BallEscapeOrder` (`auto|off|outer_first|inner_first`) orders BGA balls by ring, where ring = distance in pitches to the nearest outer row or column. "inner_first routes the innermost ring first: the balls with the fewest ways out take theirs while the grid is empty, and the outer balls, which always have the edge, follow." — [FR/autoroute/pipeline/BallEscapeOrder.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/pipeline/BallEscapeOrder.java).
- A Freerouting planning document (written by an AI assistant, 2026-06-12, "no code changes yet") describes the fan-out as "omnidirectional (no directional bias)", with "no via placement guidance" and "linear ripup cost escalation". It proposes RUDY-style congestion maps and congestion-aware pin ordering. Its survey of industry tools is unsourced — [docs/research/escape_congestion_research.md](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/docs/research/escape_congestion_research.md).

**Altium Situs [doc]**
- Fan-out passes are component-level. "Fan out Signal" (signal layers) and "Fan out to Plane" (internal plane only) both work from the Fanout Control rule: they "check for patterns in pads, consider clearance, routing width and via style, then select a suitable fan out arrangement (inline row, staggered, etc)". Fan-out options include "Fanout Outer 2 Rows of Pads", blind vias where drill pairs exist, "Include escape routes after fanout completion" (tracks from vias/pads to the component edge, with BGA escape route options) and "Escape differential pair pads first" — [Altium CircuitMaker: Situs topological autorouter](https://www.altium.com/documentation/altium-circuitmaker/automated-board-layout-situs-topological-autorouter).
- Fanout Control rule options. **Style:** Auto, Inline Rows, Staggered Rows, BGA, Under Pads. **Direction:** Disable, In Only, Out Only, In Then Out, Out Then In, Alternating In and Out. **BGA Direction From Pad:** Away From Center, North-East, South-East, South-West, North-West, Towards Center ("if existing vias block a uniform direction, each pad uses the next available diagonal"); BGA pads are split into quadrants that fan out simultaneously at 45°. **Via Placement Mode:** "Close To Pad (Follow Rules)" or "Centered Between Pads". Default rules by priority: Fanout_BGA (IsBGA), Fanout_LCC, Fanout_SOIC, Fanout_Small (CompPinCount < 5), Fanout_Default — [Altium: Routing – Fanout Control rule](https://altium.com/documentation/altium-nexus/pcb-routing-rule-fanout-control).

**Specctra / Allegro PCB Router [doc via Pulsonix; forum]**
- The `fanout` do-file command "handles escape tracks from SMD pads using vias". It is recommended for SMD boards with more than two routing layers, and its direction can put vias inside components, outside them, or both (in/out/in_out). A sample do file runs in phases: `bus diagonal`, `fanout 5`, `route 20`, `clean 2`, a second route + clean, `filter`, then `recorner` — Pulsonix's Specctra documentation ([router commands](https://pulsonix.com/docs/Advanced-Router/idh_router_commands)). The page body could not be fetched directly; these details come from the search summary of that page.
- Pulsonix's "Smart Route" front end to Specctra offers track grid, via grid, "auto breakout" (short escape tracks from SMD pads to vias) and via sharing between same-net SMD pads. It runs as many passes as needed to try to reach 100% — [Pulsonix: Specctra Smart Route](https://pulsonix.com/docs/Link-To-Specctra-Routers/idh_specctra_smart).
- A user asked about Specctra BGA quadrant-style fan-out with in/out/in_out options; no confirmed answer — [Cadence forum: fanout in specctra autorouting](https://community.cadence.com/cadence_technology_forums/pcb-design/f/pcb-design/15363/fanout-in-specctra-autorouting). In Allegro the interactive command is Route > Create Fanout — [EDAboard: BGA fanout in Allegro](https://www.edaboard.com/threads/bga-fanout-in-allegro.216200/?amp=1).

**Siemens Xpedition / PADS Professional [doc/blog]**
- Fan-out is "the process of using auto-routing technology to route short traces to a via so a net has access to internal layers". Rules cover direction, trace width, via type, allowed trace length and clearances, with three BGA fan-out options. The worked example fans out power/ground "outside" first, then the rest "inside". Via-in-pad is enabled under Editor Control > Pad Entry — [Siemens blog: Layout automation part 3](https://blogs.sw.siemens.com/electronic-systems-design/2019/10/08/layout-automation-using-advanced-pcb-design-techniques-part-3/).

**Zuken CR-8000 Dragon EX [doc]**
- BGA fan-out: draw a "Dragon area" over the package and define a strategy of steps that fan out pads by signal name. Ground pins can go to the plane through a specified via. Layers, direction and via are controllable; no-net pins get temporary nets plus "Offset Via" — [Zuken: Fanout with Design Force Dragon EX](https://www.zuken.com/en/blog/fanout-design-force-dragon-ex/), [Zuken: fanning out BGA no-net pins](https://www.zuken.com/us/blog/tech-tip-fanning-out-bga-no-net-pins/).

**tscircuit capacity-autorouter [src]**
- `AutoroutingPipelineSolver10_BgaFanout` steps: `componentDetectionSolver` → `firstBgaFanoutSolver` → `secondBgaFanoutSolver` → `autoroutingPipelineSolver` (pipeline 9). It uses the external package `@tscircuit/fanout-solver` (`FanoutSolver`, `FanoutDirection`, `FanoutBusSpec`). Constants: `MAX_FANOUT_BOUNDARY_MARGIN_MM = 4.5`, `MIN_FANOUT_BOUNDARY_MARGIN_MM = 2`, `MIN_POST_FANOUT_CORRIDOR_MM = 2`, `INWARD_ESCAPE_DEPTH_MM = 1.2`. A code comment: "The fanout solver assigns one layer to an entire bus … use per-signal physical buses here so a 25-signal address group is not incorrectly forced through one BGA layer" — [CAP/lib/autorouter-pipelines/AutoroutingPipeline10_BgaFanout/AutoroutingPipelineSolver10_BgaFanout.ts](https://github.com/tscircuit/capacity-autorouter/blob/e703f0499188f858b2b5e571ac80091d4c10733a/lib/autorouter-pipelines/AutoroutingPipeline10_BgaFanout/AutoroutingPipelineSolver10_BgaFanout.ts).
- `EscapeViaLocationSolver` (stage 3 of pipeline 9) applies only to nets that have a copper pour on another layer. For each single-layer pad point it generates candidate positions (stepped by the via-to-via clearance), requires a clear escape path, via-to-pad clearance and spacing from already placed escape vias, then picks the best by `score = 100*minClearance − distance − 0.5*|Δlayer| + 2*min(projectedFreeSpace, 3) + 10*min(minPlacedEscapeViaClearance, requiredViaToViaClearance)`. The chosen via becomes a new connection point — [CAP/lib/solvers/EscapeViaLocationSolver/EscapeViaLocationSolver.ts](https://github.com/tscircuit/capacity-autorouter/blob/e703f0499188f858b2b5e571ac80091d4c10733a/lib/solvers/EscapeViaLocationSolver/EscapeViaLocationSolver.ts).
- Pipeline 9 also has package-specific topology generators: `BgaTopologyGeneratorSolver`, `QfpTopologyGeneratorSolver`, `QfpThermalPadTopologyGeneratorSolver`, `SoicTopologyGeneratorSolver`, `ComponentTopologyGeneratorSolver` (`lib/solvers/`). These build the routing graph around packages rather than placing vias — [CAP/lib/solvers](https://github.com/tscircuit/capacity-autorouter/tree/e703f0499188f858b2b5e571ac80091d4c10733a/lib/solvers).
- One project log reports pipeline 9 routing a 33-signal AM62L LPDDR4 breakout with "11/11 traces routed for both the SoC and RAM fanouts" after a fix. It is a single case — [tscircuit: am62l-lpddr4-breakout-repro RESULTS.md](https://tscircuit.com/0hmX/am62l-lpddr4-breakout-repro/blob/RESULTS.md).

**TopoR [doc/encyclopedic]**
- TopoR "detects BGA areas and applies a special strategy", claimed to reduce via count, density and sometimes layer count (citing Luzin et al. 2008/2009 trade articles) — [Wikipedia: TopoR](https://en.wikipedia.org/wiki/TopoR).

### Inferences
- Commercial fan-out is pattern- or template-based and rule-driven, and runs before routing. Freerouting's is search-based and stops at the first via; a TraceMaker-style lattice A* would sit in the same family. Freerouting's own experience points two ways. Eager fan-out of every pin caused oscillation (14 identical passes) and, on two-layer BGAs, via walls (417 vias, 20 opens vs 2 without). Its newer passes (`DirectPinRouting`, `ExitStubs`, `BallEscapeOrder`) all move toward "route same-layer and straight exits first, via only when needed".
- The 2.5 mm minimum escape length in Freerouting's defaults stops fan-out vias from crowding against the pad ring, so they don't wall in neighbours. The "short-escape" fallback sets it to 0 when that fails.

### Gaps
- No official Cadence Specctra/Allegro PCB Router command reference (exact `fanout` options, "smart via") was retrievable; details come from Pulsonix and forums.
- Xpedition's fan-out pattern list and via-grid behaviour are not publicly documented in the sources found.
- `@tscircuit/fanout-solver` internals (how it picks BGA via positions and layers) were not read; it is a separate repository.

## Q2. How do they keep later routes and vias from blocking pin escapes (keep-outs, costs, reservation, ordering)?

### Takeaway
Freerouting protects fan-out stubs and vias by inflating their rip-up cost, using a formula that makes short pin-to-via stubs very expensive to rip in early passes. It also keeps fan-out vias through the main routing. tscircuit penalises routes and vias near future connections' endpoints inside its high-density solver, and models via capacity per mesh node. Commercial tools rely on ordering (fan-out first, then layer-pattern and main passes) and on locking or "protect" of pre-routes. No tool found uses an explicit geometric "escape-corridor keep-out" for other nets, except tscircuit's post-fan-out corridor margin constants.

### Cited Findings
- **Freerouting fan-out via protection [src]:** `MazeRipupResolver.calcFanoutViaRipupCostFactor(trace)` applies when a trace's end contacts a single-layer pin, or a `SHOVE_FIXED` two-corner trace. Its value is `max(1, (halfWidth/length)^2 * FANOUT_COST_CONSTANT)` with `FANOUT_COST_CONSTANT = 20000`, so short stubs get a very large factor. For a via obstacle the factor comes from its attached traces. The protection holds only while `!removeUnconnectedVias && ripupCosts <= 2*startRipupCosts`, so it fades after the first couple of passes — [FR/autoroute/maze/MazeRipupResolver.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/maze/MazeRipupResolver.java).
- **Freerouting general rip-up cost [src]:** `ripupCost = ctrl.ripupCosts * costFactor / detour * fanoutViaCostFactor`, where `costFactor` = the trace half-width, or for a via `max halfwidth * 0.5*(contacts−1)`, and `detour` is the obstacle connection's detour ratio. From rip-up pass 4, on passes where `pass % 3 != 0`, detour is multiplied by a random factor `0.5 + r²`, seeded with `ripupCosts` "to keep v1.9 deterministic randomization". Obstacles with user-fixed contacts cannot be ripped (returns −1) — same file.
- **Freerouting fan-out vias survive routing [src]:** `RoutingBoard.fanout` sets `removeUnconnectedVias = false`. The pass runner removes only dangling tails with `StopConnectionOption.FANOUT_VIA`, keeping fan-out vias, until a recovery step (see Q4) — [FR/autoroute/pipeline/AutoroutePassRunner.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/pipeline/AutoroutePassRunner.java) (line ~218).
- **Freerouting fixed exit stubs [src]:** `ExitStubs.PLACED_STATE = FixedState.USER_FIXED`, so the router can neither rip nor shove the designer-style exits it placed before fan-out — [FR/autoroute/pipeline/ExitStubs.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/pipeline/ExitStubs.java).
- **Freerouting ordering [src]:** `BallEscapeOrder` puts the balls with "the fewest ways out" first (`inner_first`). `BatchFanout` orders components by most SMD pins first — see Q1 sources.
- **tscircuit future-connection penalty [src]:** `HighDensityHyperParameters` includes `FUTURE_CONNECTION_PROX_TRACE_PENALTY_FACTOR`, `FUTURE_CONNECTION_PROX_VIA_PENALTY_FACTOR`, `FUTURE_CONNECTION_PROXIMITY_VD` and `FUTURE_CONNECTION_TRACE_PROXIMITY`. The intra-node A* (`SingleHighDensityRouteSolver`) receives `futureConnections` (the not-yet-routed connections in the same node) and penalises traces and vias near their points. It also has an obstacle repulsion field (`OBSTACLE_PROX_PENALTY_FACTOR` λ, `OBSTACLE_PROX_SIGMA` σ) and an edge-proximity field — [CAP/lib/solvers/HighDensitySolver/HighDensityHyperParameters.ts](https://github.com/tscircuit/capacity-autorouter/blob/e703f0499188f858b2b5e571ac80091d4c10733a/lib/solvers/HighDensitySolver/HighDensityHyperParameters.ts), [SingleHighDensityRouteSolver.ts](https://github.com/tscircuit/capacity-autorouter/blob/e703f0499188f858b2b5e571ac80091d4c10733a/lib/solvers/HighDensitySolver/SingleHighDensityRouteSolver.ts).
- **tscircuit via capacity per node [src]:** `getTunedTotalCapacity1(node)` is "how many vias the node can fit, tuned for two layers": `((sqrt(w*h)*clamp(minSide/(viaD+margin))^0.05) / (viaD/2+margin) / 2)^1.1`, with defaults `VIA_DIAMETER=0.3`, `obstacleMargin=0.2`. Single-layer nodes are capped at 1. The global path planner uses this capacity so that it does not send more layer-changing routes through a region than can hold their vias — [CAP/lib/utils/getTunedTotalCapacity1.ts](https://github.com/tscircuit/capacity-autorouter/blob/e703f0499188f858b2b5e571ac80091d4c10733a/lib/utils/getTunedTotalCapacity1.ts).
- **tscircuit escape-via spacing [src]:** each new escape via must keep `obstacleMargin` from previously placed escape vias. The score rewards via-to-via clearance and "projected free space" (capped at 3) along the escape direction — [EscapeViaLocationSolver.ts](https://github.com/tscircuit/capacity-autorouter/blob/e703f0499188f858b2b5e571ac80091d4c10733a/lib/solvers/EscapeViaLocationSolver/EscapeViaLocationSolver.ts).
- **tscircuit BGA corridor [src]:** `MIN_POST_FANOUT_CORRIDOR_MM = 2` and the boundary margins of 2–4.5 mm in the BGA pipeline keep a corridor around the fanned-out package — see Q1 source.
- **Altium [doc]:** "Lock All Pre-routes prevents pre-routed nets from being ripped up". Pass order is the strategy's "intelligence" (fan-out, Memory, Layer Patterns, Main, Completion…) — [Altium CircuitMaker Situs page](https://www.altium.com/documentation/altium-circuitmaker/automated-board-layout-situs-topological-autorouter).
- **Specctra [forum]:** one user reports that running `route`, `clean` or `filter` after `fanout` moved vias that `fanout` had placed under components. So in Specctra fan-out vias are not inherently locked unless protected — search summary of [EDAboard: specctra fanout problem](https://www.edaboard.com/threads/specctra-fanout-problem.19893/).
- **KiCad PNS [src]:** locked vias and joints are never shoved (`aVia->IsLocked()` → `SH_TRY_WALK`; `jt->IsLocked()` → `SH_INCOMPLETE`) — [KC/pns_shove.cpp](https://gitlab.com/kicad/code/kicad/-/blob/4d0814cfafc6e120a376fe418fcf5cfd15b74e97/pcbnew/router/pns_shove.cpp) `SHOVE::pushOrShoveVia`.

### Inferences
- Freerouting's protection is a cost, not a reservation, and it decays: after pass 2 (`ripupCosts > 2*start`) fan-out vias become ordinary rippable obstacles. This is a deliberate trade between protecting escapes early and letting negotiation clear them late.
- tscircuit's "future connection proximity" penalty is the closest open-source analogue of reserving pin-escape space for nets not yet routed. It only acts within a capacity node, between connections assigned to that node.
- None of the open tools reviewed adds an explicit cost for foreign vias inside another footprint's pad-ring or escape region during the main route. TraceMaker reports this as its dominant failure mode, and that looks like a gap in prior art rather than a solved problem.

### Gaps
- No public documentation of how Allegro, Xpedition or Zuken autorouters protect fan-out regions during main routing (e.g. automatic "protect" of fan-out wires) was found.
- Situs's internal costs for fan-out wiring during Main and Completion are not documented.

## Q3. How do they choose layer changes during search (via cost, via grid, layer direction preferences / "layer pattern" H-V)?

### Takeaway
Freerouting adds a flat via cost: 50 by default, 5 for plane nets, multiplied by 0.1 on "pure SMD" nets. It scales that by via radius, uses sparse gridless via candidates (centroids of free convex regions), and assigns per-layer H/V preferred-direction costs derived from the board aspect ratio, with extra cost on the outer layers when there are more than 2 layers. tscircuit's intra-node A* charges a via `cellStep + 0.3 * straightLineDistance` and adds the same term to the heuristic when off the goal layer. Specctra and Situs use preferred layer direction with a "wrong-way" cost and a via cost that can be relaxed in later passes; Situs has a "Layer Patterns" pass and a "Via Miser" strategy. TopoR has no preferred directions at all.

### Cited Findings
- **Freerouting via cost [src]:** defaults `DEFAULT_VIA_COSTS = 50` and `DEFAULT_PLANE_VIA_COSTS = 5` ("to encourage short stubs into the plane rather than long surface traces"). The plane value is used when the net contains a plane (`AutorouteConnectionRouter`). `minNormalViaCost = viaCosts * max(maxViaRadius, 1)`; for a "pure SMD net" it is also multiplied by `smdNetViaCostFactor` (default `DEFAULT_SMD_NET_VIA_COST_FACTOR = 0.1`): "Pure SMD boards need a much cheaper via escape to avoid exhausting the local pad channel before the search commits to a layer change." `minCheapViaCost = 0.8*minNormalViaCost`. Per-layer-pair extra costs live in `addViaCosts[from].toLayer[to]` — [FR/autoroute/maze/AutorouteControl.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/maze/AutorouteControl.java) (lines ~385–405), [DefaultSettings.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/settings/sources/DefaultSettings.java), [AutorouteConnectionRouter.java](https://github.com/freerouting/freerouting/blob/2eba6f7fbf7c0ca7b5aa5f8cba7136d066fb4d10/src/main/java/app/freerouting/autoroute/pipeline/AutorouteConnectionRouter.java).

- **Wrong-way relaxation [patent]:** a patent describes a high initial wrong-way cost that is lowered in later passes so the router can resolve difficult situations — [US8250514B1 Localized routing direction](https://patents.google.com/patent/US8250514).
- **Altium Situs [doc]:** routing layers have directions (the setup report warns about layers set to "Any"). The "Layer Patterns" pass "routes only connections that match a layer direction within a tolerance", costed to hug or follow existing routing. "Memory" routes same-layer pins on different components that share X or Y. A "More/Less Vias" slider trades speed against via count. The "Via Miser" strategy does "aggressive via minimization". Situs builds a triangulated topological map from the relative positions of obstacles, then turns paths into tracks with push-and-shove — [Altium CircuitMaker Situs page](https://www.altium.com/documentation/altium-circuitmaker/automated-board-layout-situs-topological-autorouter), [Altium: Situs Routing Strategies](https://www.altium.com/documentation/cstu/situs-routing-strategies).
- **TopoR [encyclopedic/vendor claim]:** "absence of preferred routing directions" and any-angle and arc wires. It optimises several layout variants at once and discards those with the worst total length and via count. A single-layer algorithm minimises interlayer junctions (Polubasov 2001) — [Wikipedia: TopoR](https://en.wikipedia.org/wiki/TopoR). Wire shape is computed from the topological path by a minimum-length-path algorithm under design rules — [ITMO journal: Calculation of the minimum path length wire in topological routing](https://ntv.ifmo.ru/en/article/3839/CALCULATION_OF_THE_MINIMUM_PATH_LENGTH_WIRE_IN_THE_PRINTED_WIRING_TOPOLOGICAL_ROUTING.htm).
- **JITX [doc]:** the topological autorouter "works on one layer at a time"; vias are routeable endpoints like pads, and the page does not say how it decides on layer changes — [JITX: Topological Autorouter](https://docs.jitx.com/en/4.0/essentials/physical_design/autorouter.html).

### Inferences
- Two open routers made the same discovery from different directions. Freerouting cuts the via cost tenfold for pure-SMD nets because otherwise the search "exhaust[s] the local pad channel before … commit[ting] to a layer change". tscircuit makes via cost proportional to the connection's length. Both argue against a flat, high via cost near dense SMD pins. A flat cost pushes the search to burn same-layer escape space before trying the via-and-other-layer option that TraceMaker's users can see.
- Freerouting's sparse via candidates (one per convex free region) let it evaluate layer changes cheaply anywhere. A lattice router evaluating vias at every lattice point pays much more per layer-change option.

### Gaps
- No primary Cadence document on "smart via" was found; the term could not be verified.
- Xpedition's via grid / layer-bias costs and Zuken's layer-change costing are undocumented in the public sources found.

## Q4. What do they do in the last pass to finish the last few connections (via pushing, shove, rip-up with growing costs, "clean-up", "smooth")?

### Takeaway
Freerouting stacks several targeted end-game mechanisms on top of linearly growing rip-up cost:
- a one-time removal of fan-out tails and vias after 3 stagnant passes;
- a "last-mile" rip-up of up to 24 foreign traces and vias inside the bounding boxes of the remaining airlines, when 8 or fewer remain;
- growing-radius neighbourhood rip-up around open pins;
- whole-board re-runs under named setting changes (fan-out retry, short or open escape window, direct-first, no fan-out), keeping the best result;
- via shoving during insertion.

Commercial routers use rising conflict cost until conflicts are prohibited, a costed "Completion" pass (Situs), and clean/filter/recorner passes. KiCad's PNS (interactive only) pushes vias by a force vector and walks around pads.

### Inferences
- Freerouting's end game is targeted removal of foreign copper near the remaining airlines, followed by more negotiated passes, and whole-run portfolio restarts with fan-out and escape-window variants. It moves no vias in the end game except by trace-shove during insertion. Both `LastMileBlockerRipup` (airline bounding box, ≤24 items) and `RetryNeighbourhood` (1.5 → 12 mm radius around open pins) map directly onto TraceMaker's case of open connections blocked by foreign vias in a fan-out region.
- KiCad's force-vector via push (move the via, drag its stubs, never move pads) is the clearest open reference for "via relocation" as a repair step, though it is interactive.

### Gaps
- No public detail on Allegro's or Xpedition's final-completion algorithms (e.g. whether they push vias automatically) was found.
- The internals of Situs "Completion" costing are undocumented.

### Inferences
- Freerouting's jump from about 50% to about 91% fully routed between 1.9 and 2.6 came in the same releases that added the fan-out, escape and fallback machinery listed above (version 2.5 onward; the migration docs credit freerouting.net). This is correlation from the changelog and benchmark timing, not an ablation. Even so, dense Tier C stays at about 70%, so its techniques do not close hard boards reliably.
- DeepPCB's own tables show that 28% of 4-layer boards with 201–500 airwires finish below 95% completion. Vendor "near-100%" medians hide a hard tail like TraceMaker's.

### Gaps
- No independent, cross-tool benchmark of completion on hard boards (same boards, same rules) was found.
- No published aggregate tscircuit completion number on the srj datasets was found in the repo docs or blog.
- No published completion figures for Situs, Specctra/Allegro PCB Router, Xpedition or Zuken autorouters on dense boards were found.
