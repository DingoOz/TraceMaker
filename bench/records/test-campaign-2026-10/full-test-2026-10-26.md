## 2. GPU against CPU fields (rule 3) with both GPUs free

- **33 tricky boards, 3 M work, 3 x 8 threads: 33/33 byte-identical** between GPU fields (`full-g-det8`) and last night's CPU fields
  (`soak-c-det8`); 0 added errors.
- **But the GPU path is slower even with free GPUs**: route CPU time 1,836 → 2,213 s (+20 %), sum of wall times 362 → 458 s; per
  board -3 % to +70 %. interf_u, 8 threads, `--no-kb`: same board (`2e994c22`) both ways, 743 fields all on the GPU (0 fallbacks),
  **74.8 s of field time on the GPU against 25.3 s on the CPU**; route 32.3 s vs 15.1 s. With eight variant threads sharing a GPU and
  grids this small, launch, copy and queueing cost more than the GPU saves. Combined with the fallback cliff of the soak (driver-lock
  waits when the GPUs are full), the GPU path is slower on every board measured so far. Suggestion (not made): default to CPU fields
  and use the GPU only above a grid-size threshold that a measurement sets, or make `--no-gpu` the default until then.
- **GPU fields, 3 x 8 against 6 x 4 threads** (six boards sharing two GPUs): **33/33 byte-identical** (`full-g-det4`).
- **P100 only** (`CUDA_VISIBLE_DEVICES` = its UUID, sm_60): **33/33 byte-identical** to both GPUs (`full-g-p100`).
- **V100 only** (sm_70): **33/33 byte-identical** (`full-g-v100`). So CPU, P100, V100 and both GPUs give the same 33 boards.
- **30 M work: 33/33 byte-identical** between GPU fields (`full-g-w30`) and CPU fields (`soak-c-w30t8`).
- Speed caveat: the CPU baselines above ran last night with other jobs on the machine, so their times are not comparable; the
  interf_u pair (same moment, idle machine) is. CPU-field reruns on the idle machine are queued (`full-c-det8`, `full-c-w30`).

## 5. Harness bug: `bench/viewport.py` runs out of viewer ports on fast board sets

`full-srj19` stopped after 4 boards, `full-srj20` and `full-pcbworld` at their first, with `RuntimeError: no free viewer port`
(`bench/viewport.py` `new_port`). Ports 8800-8899 are claimed for `CLAIM_S = 300` s each and the claim is not released when the route
ends, so any run finishing more than 100 boards in 5 minutes (srj19: 3-6 s per board, 12 jobs) exhausts them; `.view-claims` held 98
fresh claims. Suggested fix (not made): release the claim when the route exits (run.py knows), or reuse a claimed port once it is
free again. Workaround tonight: rerun those sets one board at a time (srj) or two (PCBWorld), with `--view` kept (`queue4.sh`).

## 6. Fair GPU-vs-CPU speed on the tricky boards (both on the idle machine)

- **3 M work, 3 x 8 threads: 33/33 byte-identical; GPU route CPU time 2,213 s against 1,827 s on the CPU (+21 %)**, router wall
  435 vs 356 s (`compare-speed-3m.txt`, `full-c-det8` vs `full-g-det8`).
- **30 M work, 3 x 8 threads: 33/33 byte-identical; GPU route CPU time 15,192 s against 17,857 s on the CPU (-15 %)**, router wall
  2,862 vs 3,615 s (`compare-speed-30m.txt`). Here the GPU path is faster.

**Correction to section 2/3:** the GPU path is not slower everywhere. Measured fairly (idle machine, consecutive runs):

| Run | Threads sharing 2 GPUs | GPU vs CPU route CPU time |
|---|--:|--:|
| quick, 1 M work, 12 x 8 (default jobs) | 96 | +138 % |
| mid, 20 M work, 6 x 8 | 48 | +56 % |
| tricky boards, 3 M work, 3 x 8 | 24 | +21 % |
| tricky boards, 30 M work, 3 x 8 | 24 | **-15 %** |
| interf_u alone, 3 M work, 8 threads | 8 | +114 % (32 s vs 15 s) |

The GPU pays only on long runs with few threads per GPU; short runs and many concurrent callers lose. The answer is not "turn the
GPU off" but a measured rule (e.g. by grid size and callers per device), plus the fallback fix of the soak. A proper study would vary
one factor at a time; these runs differ in board set too.

## 9. Sanitizer test suites

- **`ctest --preset asan`: 383/391 passed, 1 failed, 7 skipped** (5 GPU tests: the asan preset has no CUDA; `python_bindings`;
  `fixture_preparation_native`), 2,127 s, no AddressSanitizer or LeakSanitizer report.
  **Failed: `Copper text boxes cover KiCad's stroke-font advances`** (`tests/test_kicad_measured_shapes.cpp:27`), every time, with the
  libstdc++ assertion `std::vector<NetClass>::front(): Assertion '!this->empty()' failed`. The test builds a default
  `model::DesignRules` (no classes) and passes it to `route::Obstacles`, whose constructor calls `default_class()`
  (`src/route/obstacles.cpp:682`), which is `classes.front()` (`src/model/rules.hpp:74`) on an empty vector: undefined behaviour,
  which the release build survives by luck. Production is not affected: `io::kicad` `read_rules` always inserts a "Default" class
  (`project_reader.cpp:295`). The test arrived on 21 October (`6288c12`, D132/D133); the 0.11.0 release ran only the `release`
  suite, so no sanitizer suite has run since. Fix (not made): give the test's rules a Default class, and make `default_class()` assert
  or fall back instead of reading past an empty vector.
- **`ctest --preset tsan`: 382/391 passed, 2 failed, 7 skipped**, 3,347 s, **0 data races**. Failed: the same stroke-font test
  (same assertion), and **`round_options` (timeout at 600 s)**, which is slowness, not a hang: it takes 27 s in release and 555 s
  under ASan, so its 600 s limit (`tests/CMakeLists.txt:78`) is too tight for the sanitizer builds (`bus_route` already has 3,600 s
  with a comment saying why). The output holds 36 TSan warnings, all "signal-unsafe call inside of a signal" in Catch2's fatal-signal
  handler (`Catch::RunContext::handleFatalErrorCondition`, the JUnit reporter), i.e. Catch2 reporting the stroke-font test's abort;
  they go away with that fix.
